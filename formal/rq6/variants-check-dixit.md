# 문헌 변형 재구현 점검 결과: Dixit·Khuteta 2017 (R6-04, 해석별 정책 여섯 개)

`bench/check_variants_dixit.py`가 쓴 결과다. AI(Claude)가 작성한 초안이며 사람의 검토 전이다. 변형은 오라클과 비교하지 않는다(불일치가 K1이 재는 대상이다). 문헌 예제 재현, 같은 해석의 두 번째 독립 구현과의 차등, 속성을 본다. 이 점검은 오라클도, 오라클의 정의(닫힘 계산)를 따로 옮긴 함수도 쓰지 않는다. 아래 '관찰'은 문헌 예제의 재현 결과이며 주장 판정이 아니다. 논문의 숫자는 제3자 사본(SlideShare)의 본문을 도구가 읽어 낸 텍스트에서 옮겼고 저널 PDF와는 아직 대조하지 않았다.

## 1. 옮긴 표의 정합성과 예제 재현

Need = Max − Allocation(다섯 행 모두), Max ≤ 총량, 총량 − ΣAllocation = [0, 2, 3](인쇄된 Available과 같음). 옮긴 값을 일부러 틀리게 한 표 둘을 이 정합성 점검이 잡는다(비공허성).

여섯 정책이 예제에서 낸 결과다. 훑기의 추적(P0·P1 스택, P2 스택과 정리, P3 실행, P4 스택과 정리)과 훑기 뒤의 스택 순서(위에서 P2, P4, P1, P0)는 여섯 정책이 모두 인쇄된 것과 같다(P3을 실행하기 전에는 release와 tail이 영향을 주지 않고, P3 뒤의 P4 판단은 이 예제에서는 두 release에서 같다). 달라지는 것은 P3 뒤의 Available과 스택의 처리다.

| 정책 | 실행한 순서 | 스택에 남음(위→아래) | P3 실행 뒤 Available | 끝났을 때 Available | 판정 |
|---|---|---|---|---|---|
| dixit-max-once | P3 | P2, P4, P1, P0 | (2, 3, 4) | (2, 3, 4) | 불안전 |
| dixit-max-top | P3, P2, P4, P1, P0 | — | (2, 3, 4) | (11, 5, 10) | 안전 |
| dixit-max-repeat | P3, P2, P4, P1, P0 | — | (2, 3, 4) | (11, 5, 10) | 안전 |
| dixit-alloc-once | P3 | P2, P4, P1, P0 | (2, 1, 1) | (2, 1, 1) | 불안전 |
| dixit-alloc-top | P3 | P2, P4, P1, P0 | (2, 1, 1) | (2, 1, 1) | 불안전 |
| dixit-alloc-repeat | P3 | P2, P4, P1, P0 | (2, 1, 1) | (2, 1, 1) | 불안전 |

논문은 스택의 프로세스가 '위에서부터 실행된다'고 쓰고 단계별 Available도 최종 안전 순서도 인쇄하지 않는다. 위 표의 관찰은 다음과 같다. (가) release="max"(Allocation을 받은 뒤의 보유량으로 읽음)에서는 top과 repeat이 스택을 인쇄된 순서(P2, P4, P1, P0) 그대로 모두 실행하고 끝난 뒤 Available이 총량 (11, 5, 10)이 된다. (나) release="alloc"(인쇄된 식을 글자 그대로 읽음)에서는 P3을 실행한 뒤 Available이 (2, 1, 1)로 줄어 스택의 어느 프로세스도 실행되지 못한다. 논문이 스택의 프로세스가 실행된다고 쓰므로 (나)의 읽기는 논문의 서술과 맞지 않는다. 이는 AI의 해석이며 저자의 뜻을 확인한 것이 아니다.

문장 그대로의 '미만' 읽기(Need < Available, 모든 성분이 엄격히 작음)에서는 첫 단계의 P3(Need = Available)이 실행되지 않아 인쇄된 추적과 맞지 않는다(변이체 strict-fit의 결과: 실행한 순서 (없음), 불안전 예). 그래서 비교는 '≤'로 읽었다.

### 1.1 인쇄된 스택 순서와 맞는 정렬 키 (도출 D10, AI)

논문은 스택을 '필요량이 작은 것이 위'로 정리한다고만 쓰고 필요량 벡터의 크기를 비교하는 규칙을 쓰지 않는다. 예제의 인쇄된 순서(P2, P4, P1, P0)를 재현하는 키 후보다.

| 키 | 스택 순서(위→아래, 같은 키는 번호 순) | 인쇄된 순서와 같은가 |
|---|---|---|
| Need 성분의 합 | P2, P4, P1, P0 | 예 |
| Need의 제곱합 | P2, P4, P1, P0 | 예 |
| Max 성분의 합 | P2, P4, P1, P0 | 예 |
| Need 성분의 최댓값 | P2, P1, P4, P0 | 아니오 |
| Need의 사전식 순서 | P4, P2, P1, P0 | 아니오 |
| Allocation 성분의 합 | P1, P2, P0, P4 | 아니오 |
| Need의 최솟값 | P4, P2, P0, P1 | 아니오 |

예제와 맞는 키가 여럿이므로 예제로는 키를 정할 수 없다. 이 구현은 가장 단순한 'Need 성분의 합'을 썼다. 점검 입력 23148개에서 max-top의 판정이 Need 합 대신 제곱합을 쓰면 34개, Max 합을 쓰면 203개에서 달라졌다(변형 사이의 비교이며 오라클과의 비교가 아니다).

`sca_cmp`는 Need ≤ Available 확인의 스칼라 비교(단락 평가)와 스택 정리의 키 비교(`sort_cmp`)를 더한 값이다. 교재식 구현의 `vec_add`는 끝낸 프로세스마다 1번이고 이 알고리즘은 Available에서 Need를 빼고 되돌리는 2번이다. 교재식 구현에는 정렬이 없다.

## 2. 두 번째 독립 구현과의 차등

스택을 파이썬 리스트(끝이 위)로 두고 넣을 때마다 전체를 정렬하는 기계(`literal_dixit`)와 여섯 정책 각각을 비교한다. 정리의 비교 횟수는 '위에서부터 자기보다 큰 키를 만날 때까지'의 식으로 센다. 비교 항목은 실행한 순서, 불안전 여부, 남은 스택, 계측 계수(vec_cmp, sca_cmp, vec_add, iters, sort_cmp, key_add, pushes, rounds)다. 입력은 문헌 예제와 소규모 전수 일부, 층화 무작위(F-rand형) 일부, 경계 상태, 값이 큰 무작위 상태를 합한 35,419개이고 여섯 정책으로 212,514회 실행했다(등록된 입력군이 아니다). 불일치 0건. 시간 9.8초.

## 4. 도출 (AI, 사람 검토 대기)

- **D7 (max-repeat의 판정, 코드로 확인하지 않음)**: release="max"이고 tail="repeat"인 읽기는 안 끝난 프로세스를 되풀이해 훑고 진전이 없을 때 멈추므로 끝낸 집합이 닫힘(순서와 무관한 가장 큰 완료 가능 집합)이고, 따라서 판정이 교재식 닫힘 계산(`docs/rq6/reference.md` §2)과 같을 것이다. 정렬된 스택은 비용과 안전 순서만 바꾸고 판정은 바꾸지 않을 것이다. 이는 도출이며 증명하지 않았고, 동결 전에 변형의 판정을 오라클·닫힘 계산과 대조하지 않는 규칙 때문에 코드로도 확인하지 않았다(동결 뒤에 확인한다). 이 점검이 본 간접 증거는 아래 D8의 '번호 순열에 대해 max-repeat의 판정이 변하지 않음'뿐이다.
- **D8 (실행 순서 의존)**: 프로세스 번호를 모든 순열로 바꿔 판정이 달라지는 상태의 수(소규모 전수의 일부 14912개 중): dixit-max-once 9737, dixit-max-top 790, dixit-max-repeat 0, dixit-alloc-once 3103, dixit-alloc-top 672, dixit-alloc-repeat 374. max-repeat는 0이다(D7의 서술과 맞는다). 반면 훑기를 번호 순으로 한 번만 하는 읽기(once)와 스택 위만 보는 읽기(top)는 번호에 의존하고, release="alloc"의 repeat도 의존한다(Available이 줄어들 수 있어 실행 순서에 따라 갈린다).
  - alloc-repeat의 예: 총량 [2, 2], Allocation [[0, 0], [0, 1], [0, 0]], Need [[0, 0], [0, 1], [0, 1]], Available [2, 1]. 번호 순열 3개에서는 안전, 3개에서는 불안전이다. 이 상태에는 교재식 안전 순서 [0, 1, 2]가 있다(되짚기로 확인한 증명서).
- **D9 (top이 불안전이라 하는데 교재식 안전 순서가 있음: 거짓 불안전의 최소 예)**, 최소 예(키가 같은 프로세스가 있을 수 있음): n = 3, 총량 (1, 1), Allocation [[0, 0], [0, 1], [1, 0]], Need [[0, 1], [1, 0], [0, 0]], Available [0, 0]. 훑기에서 실행한 뒤 스택의 위(번호 0)가 실행되지 못해 top은 불안전을 돌려주지만 repeat는 모두 끝내고 그 실행 순서 [2, 1, 0]가 교재식 안전 순서임을 되짚기로 확인했다(스택 [0, 1]). 같은 (n, 총량)의 열거 순서에서 115번째 상태다.
- **D9 (top이 불안전이라 하는데 교재식 안전 순서가 있음: 거짓 불안전의 최소 예)**, 키가 모두 다른 최소 예: n = 3, 총량 (2, 1), Allocation [[0, 0], [0, 1], [1, 0]], Need [[0, 1], [2, 0], [0, 0]], Available [1, 0]. 훑기에서 실행한 뒤 스택의 위(번호 0)가 실행되지 못해 top은 불안전을 돌려주지만 repeat는 모두 끝내고 그 실행 순서 [2, 1, 0]가 교재식 안전 순서임을 되짚기로 확인했다(스택 [0, 1]). 같은 (n, 총량)의 열거 순서에서 395번째 상태다.
  Begum 외의 D1(`variants-derivations.md`)과 같은 종류의 도출이다: 가장 작다고 이름 붙은 필요량이 실행 가능한 프로세스를 가리지 못한다(벡터 필요량은 전순서가 아니다).
- **D10**: 위 §1.1.

점검 69개: 모두 통과. 총 시간 46초.

## 범위와 한계

- 이 점검은 '구현이 논문의 서술(의사코드 네 줄과 예제 설명)을 옮긴 해석과 같다'는 것과 '논문 예제를 재현한다'는 것만 본다. 해석이 저자의 뜻과 같다는 보장은 없다. 논문의 의사코드에는 스택 처리, 갱신식의 첨자, 정렬 키, 종료 조건이 없어 여섯 정책은 서로 다른 보완이다(docs/rq6/variants.md §5.2의 해석 목록).
- 두 번째 구현은 같은 사람이 같은 이해로 쓴 것이다. 구조가 달라 옮기다 생기는 실수는 잡지만 해석의 오류는 잡지 못한다.
- 논문의 값은 제3자 사본의 본문을 도구가 읽어 낸 텍스트에서 옮겼다. 값 사이의 중복(Need = Max − Allocation, 총량)으로 정합성을 점검했으나 저널 인쇄본과의 일치를 보장하지는 않는다.
- 논문의 정량 주장(그림 2, 평균 약 9%)은 곡선 값과 실행 조건이 없어 재현하지 못한다. 이 점검은 K2·K3를 재지 않는다.
- 논문의 추상은 실행 중 자원 수를 바꿀 수 있다고 쓰나 알고리즘, 표, 예제에 그 내용이 없다. 구현하지 않았다.
- 소규모 전수에 쓴 oracle.banker.all_states는 상태를 나열하는 데만 썼고 오라클의 판정은 부르지 않았다. 오라클(O1)과의 비교와 등록된 입력군 위의 비용·시간은 동결 전에 하지 않았다.
