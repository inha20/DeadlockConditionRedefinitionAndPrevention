## 0. 이 문서가 하는 일과 하지 않는 일

**하는 일.** `prereg/RQ5.md` §4가 이름만 정한 변수 V1–V13의 정의, 값, 결정 규칙, 변수 사이의 모순 규칙, 불확실 처리, 파일럿과 일치도 절차, 코딩 표의 형식을 정한다. 코더 1(사람)과 코더 2(AI)가 같은 규칙으로 읽도록 하는 것이 목적이다.

**하지 않는 일.**
- 이 초안을 쓰는 동안 E2 데이터셋의 49개 커밋을 하나도 읽지 않았다. 아래의 경계 예는 모두 이 문서를 위해 **구성한 것이며 실제 사례가 아니다**. 그래서 정의가 실제 사례를 잘 가르는지는 모른다. 파일럿이 처음으로 시험한다.
- 커널 지식은 AI의 일반 지식과 문헌 요약(문서 05 §6.2)에서 왔다. 커널 전문가의 확인을 받지 않았다(열린 항목 O5-1). 문헌 서술은 대부분 도구 요약(A−)이나 초록(B)이며 원문 재확인 전이다.
- 결과를 말하지 않는다. 어떤 변수의 비율도 이 문서에 없다.
- `prereg/RQ5.md` §4와 다른 부분(§7)은 **제안**이다. 사람이 승인하기 전에는 prereg의 표가 정본이다(열린 항목 O5-12).
- 이 코드북의 초안도 AI가 썼다. 코더 2가 같은 AI이면 코더 2의 해석이 코드북의 해석과 닮도록 쓰였을 가능성이 있어 κ가 높게 나올 수 있다(독립성 한계, prereg §4).

## 1. 코딩 단위, 정보원, 기록

**단위.** 커밋 하나가 한 사례다(E2의 한 행, 40자 소문자 16진수 해시). 한 커밋이 교착을 둘 이상 고치면 커밋 메시지가 말하는 주된 것을 코딩하고 `note`에 적는다(prereg §4). 49건은 모두 포함하고 제외하지 않는다. 읽을 수 없는 커밋도 제외하지 않고 모든 변수를 `uncertain`으로, 사유를 `U1`로, `evidence`에 읽을 수 없는 이유를 적는다.

**정보원(`sources`).** 코딩 때 실제로 본 것을 `+`로 잇는다(사전순). 값은 다음과 같다.

| 값 | 뜻 |
|---|---|
| `ml` | 커밋 메시지가 링크한 메일링 리스트 논의 |
| `msg` | 커밋 메시지 |
| `other` | 위에 없는 것(문서, 참조한 소스 파일 등). 무엇인지 `note`에 적는다 |
| `patch` | 패치(diff)와 그 주변 소스 |

**코더(`coder`), 회차(`round`), 상태(`status`).**

| 열 | 값 | 뜻 |
|---|---|---|
| `coder` | `c1` | 코더 1(사람) |
| | `c2` | 코더 2(AI) |
| | `final` | 불일치를 해소한 최종 판정(사람) |
| `round` | `pilot1` | 첫 파일럿(10건) |
| | `pilot2` | 두 번째 파일럿(다른 10건. 첫 파일럿이 합격선에 못 미칠 때만) |
| | `main` | 본 코딩(49건 전체. 파일럿 사례도 다듬은 코드북으로 다시 코딩해 포함, prereg §4) |
| | `final` | 최종 판정 행 |
| `status` | `coded` | 그 코더의 코딩이 끝남 |
| | `needs_expert` | 전문가 검토 필요(불확실 사유 `U2`가 있거나 토의로 해소되지 않음) |
| | `resolved` | 불일치나 전문가 검토가 해소되어 확정됨 |

(커밋, 코더, 회차)는 표 안에서 유일해야 한다. 코더별·회차별로 파일을 따로 두고(`analysis/rq5/coding/<회차>-<코더>.csv`), 최종 판정은 `analysis/rq5/coding.csv`(`coder=final`, `round=final`)에 모은다.

**근거(`evidence`).** 코딩한 행(`coded`, `resolved`)은 비어 있으면 안 된다. 본문을 옮겨 적지 않고 위치만 적는다: 메시지의 줄 번호, 파일·함수, 메일 제목. 형식은 자유다(예: `msg:L2-4; patch:<파일>:<함수>`).

**E2의 열을 보지 않는다.** 코딩하는 동안 E2 데이터셋의 분류 열(인터럽트 의존 여부, 하드웨어 의존 여부, 실행 문맥 수, 동기화 오용, 발견 경로)을 보지 않는다. E2의 열과의 교차는 분석 시점에 외부 복제본에서 계산한다(prereg §4, §5). 코딩이 E2의 판단에 끌리지 않게 하려는 제안이다(열린 항목 O5-12).

**읽는 순서(권고).** ① 메시지에서 누가 무엇을 쥐고 무엇을 기다리는지 적는다. ② V5–V7(락 수, 자기 대기, 문맥 수)을 정한다. ③ V1–V4. ④ V8, V9, V11. ⑤ V10. ⑥ V12, V13. 요청을 낸 쪽과 쥔 쪽을 먼저 정하면 나머지 변수가 거의 따라온다.

## 2. 변수

값 이름은 코딩 표에 쓰는 문자열이다. 모든 변수에 `uncertain`이 있다(§3.3). 집합 값 변수(V2, V3, V9)는 해당하는 값을 모두 사전순으로 `+`로 잇는다(예: `hardirq+process`). `uncertain`과 V9의 `no`는 다른 값과 함께 쓰지 않는다. "구성한 예"는 이 문서를 위해 지은 것이다.

### V1 요청 자율성

질문: 교착을 이루는 요청 가운데 가장 비자율적인 것은 어떻게 일어나는가. 고전 모델은 요청을 프로세스가 자기 실행 문맥에서 스스로 낸다고 가정한다(모델 명세 §2.3의 A4, 문서 05 §6). 이 변수는 그 가정이 사례에서 깨지는지를 가른다.

| 값 | 뜻 |
|---|---|
| `own` | 모든 요청이 그 흐름 자신의 실행에서, 패치에서 보이는 직접 호출 사슬로 나온다 |
| `irq_reentry` | 요청 하나가 락을 쥔 흐름을 같은 CPU에서 선점한 인터럽트·softirq 처리기에서 나온다. 처리기가 끝나기 전에는 보유자가 한 걸음도 진행하지 못한다 |
| `indirect_reentry` | 요청이 락을 쥔 구간 안에서 간접 호출(함수 포인터, 연산 테이블, 콜백)을 거쳐 나오고, 호출 대상이 직접 호출 사슬에는 드러나지 않는다 |
| `other` | 위 셋이 아닌 비자율 메커니즘(예: 예외·폴트 진입, 시그널 전달). 메커니즘을 `note`에 적는다 |
| `uncertain` | 판단할 수 없다. 사유 필수 |

**우선순위.** 여러 값이 겹치면 `irq_reentry` > `other` > `indirect_reentry` > `own` 순으로 앞의 값을 쓴다(가장 비자율적인 요청이 값을 정한다).

**재개 불가 시험.** `irq_reentry`의 기준은 "요청을 낸 처리기가 끝나기 전에는 락 보유자가 재개할 수 없는가"다. 스레드 전환은 전환된 스레드가 다시 실행되어 락을 풀 수 있으므로 이 의존을 만들지 못하고, 처리기가 보유자 위에 쌓이는 것은 만든다는 S35의 구분과 같은 취지다(문서 05 §6.4 5d, 대장 C-SUR-173. 요약 수준 A−).

**`indirect_reentry`는 모델의 문제가 아니라 분석의 문제다.** 요청 자체는 그 흐름의 실행에서 나오므로 모델 쪽에서는 자율 요청이다. 호출 대상이 정적으로 드러나지 않는다는 점이 다를 뿐이며 요청 집합의 불확실성으로만 서술한다(prereg §2). 그래서 V8의 `classic2`, `self_only`와 함께 올 수 있다(§3.1의 C2, C3).

**경계 예(구성한 예).**
- 함수 `f`가 락 `L`을 쥔 채 `g`를 직접 호출하고 `g`가 `L`을 다시 얻는다 → `own`.
- `f`가 `L`을 쥔 채 객체의 콜백 필드를 부르고, 등록될 수 있는 콜백 중 하나가 `L`을 얻는다 → `indirect_reentry`.
- 프로세스 문맥이 해당 인터럽트를 켠 채 `L`을 쥔 동안 같은 CPU에서 인터럽트 처리기가 `L`을 얻으려 한다 → `irq_reentry`.
- CPU0의 처리기가 CPU1의 프로세스가 쥔 락을 기다리고 CPU1의 프로세스는 처리기가 쥔 락을 기다린다. 처리기는 보유자를 선점하지 않았으므로 처리기를 별도 흐름으로 보아 `own`(V2에 `hardirq`).
- 처리기가 선점한 문맥이 아무 락도 쥐지 않았다 → 그 처리기의 요청은 선점과 무관하다. `own`.
- 락을 쥔 구간에서 사용자 메모리 접근이 폴트를 일으키고 폴트 처리 경로가 같은 락을 얻는다 → `other`. 이런 비인터럽트 암묵 진입을 `other`로 두는 것이 맞는지는 전문가가 확인할 일이다(U2).
- 판단 근거가 메시지에 없다 → `uncertain`(`U1`). 어느 값인지 정의가 가르지 못한다 → `uncertain`(`U3`).

### V2 문맥 종류

질문: 교착 집합에서 락을 쥐거나 요청하는 실행 문맥은 어떤 종류들인가. 집합 값 변수다.

| 값 | 뜻 |
|---|---|
| `hardirq` | 하드웨어 인터럽트 처리기(상반부) |
| `other` | 아래 넷이 아닌 문맥(예: NMI). 종류를 `note`에 적는다 |
| `process` | 프로세스 문맥. 커널 스레드와 워크큐 작업자를 포함한다 |
| `softirq` | softirq와 그 위에서 도는 하반부 처리(태스크릿, 타이머 콜백 등) |
| `threaded_handler` | 스레드 문맥에서 실행되는 인터럽트 처리기. 해당 인터럽트가 켜진 채 실행될 수 있어 "모든 처리기는 인터럽트를 끄고 돈다"는 lockdep의 가정(T13의 서술, 2009년 시점. C)이 깨질 수 있다 |
| `uncertain` | 판단할 수 없다. 단독으로만 쓴다 |

**규칙.** 교착을 이루는 쥠과 요청에 관여한 문맥만 센다. 같은 종류가 둘이면 한 번만 적는다(프로세스 둘 → `process`).

**경계 예(구성한 예).** 스레드 둘의 AB-BA → `process`. 처리기가 프로세스를 선점하는 자기 교착 → `hardirq+process`. 같은 CPU의 하반부 처리와 프로세스 → `process+softirq`. 어느 종류인지 코드만으로 알 수 없다 → `uncertain`(`U2`).

### V3 락 종류

질문: 교착에 관여한 대기 대상은 어떤 종류인가. 집합 값 변수다. 락이 아닌 대기를 따로 둔 것은 모델 명세 §2.3이 통신·조건 변수·세마포어 신호 대기에 의한 교착을 SM v0.1의 범위 밖에 두었고, 락 순서 모델 밖의 대기를 따로 추적하는 도구가 있기 때문이다(S38 표지 글, 문서 05 §6.2).

| 값 | 뜻 |
|---|---|
| `mutex` | 잠드는 상호 배제 락 |
| `non_lock_wait` | 락이 아닌 대기: 완료 신호, 대기 큐 이벤트, 플러시·동기화 대기 등 다른 흐름의 신호를 기다리는 것 |
| `other_lock` | 위에 없는 락 형태의 기본 연산(예: 시퀀스 락, 비트 락). 무엇인지 `note`에 적는다 |
| `rwsem_rwlock` | 읽기-쓰기 세마포어와 읽기-쓰기 락(데이터셋에는 `rwsem`과 `rw_semaphore`가 섞여 있어 하나로 묶는다) |
| `semaphore` | 계수 세마포어 |
| `spinlock` | 바쁜 대기 락 |
| `uncertain` | 판단할 수 없다. 단독으로만 쓴다 |

**경계 예(구성한 예).** 뮤텍스 둘의 순환 → `mutex`. 스핀락을 쥔 채 완료 신호를 기다리고 신호를 내는 쪽이 그 스핀락을 필요로 한다 → `non_lock_wait+spinlock`.

### V4 동일 클래스 중첩

질문: 같은 클래스의 락을 쥔 채 같은 클래스의 락을 요청하는 흐름이 교착 집합에 있는가. 같은 인스턴스를 다시 얻는 경우를 포함한다. 락 클래스는 같은 종류 객체의 같은 락을 한 단위로 보는 lockdep의 단위를 따른다(S1). 패치만으로 클래스를 알 수 없으면 락이 든 객체의 타입과 초기화 위치로 짐작하고 `note`에 쓴다.

| 값 | 뜻 |
|---|---|
| `yes` | 있다 |
| `no` | 없다 |
| `uncertain` | 판단할 수 없다 |

`yes`는 위반이라는 뜻이 아니다. 서브클래스를 달아 구분한 중첩(lockdep의 `_nested()`류, S1)도 `yes`다. V9의 `dup`은 구분 표시가 없어 lockdep이 문제 삼는 경우만 가리키므로 `dup`이면 V4는 반드시 `yes`다(§3.1 C5).

### V5 관여 락 수

질문: 교착 집합의 쥠과 요청에 쓰인 서로 다른 락 객체는 몇 개인가. 락 객체와 클래스를 구분할 수 없으면 클래스로 세고 `note`에 쓴다. 지나가기만 하는 보호용 락은 세지 않는다.

| 값 | 뜻 |
|---|---|
| `1` | 하나 |
| `2` | 둘 |
| `3plus` | 셋 이상 |
| `uncertain` | 판단할 수 없다 |

락이 아닌 대기만 얽혀 있고 락이 없으면 쥔 락 기준으로 센다. 두 흐름의 순환은 단위 용량 락 둘 이상을 쓰므로 V8의 `classic2`는 V5가 `2` 또는 `3plus`일 때만 가능하다(§3.1 C2).

### V6 자기 대기

질문: 실행 흐름 하나가 이미 쥔 것을 스스로 기다리는가(길이 1 사이클). 흐름은 E2의 스레드 수 규칙처럼 센다: **인터럽트 처리기를 별도 스레드로 세지 않는다**. 같은 CPU에서 처리기가 보유자를 선점해 보유자가 쥔 락을 요청하면 한 흐름이 자기 자신을 기다리는 것으로 본다(Q5-1의 '인터럽트 재진입에 의한 단일 스레드 자기 교착'). V7과 다르다: V7은 처리기도 별개 문맥으로 센다.

| 값 | 뜻 |
|---|---|
| `yes` | 한 흐름만으로 교착이 된다 |
| `no` | 둘 이상의 흐름이 있어야 교착이 된다 |
| `uncertain` | 판단할 수 없다 |

**경계 예(구성한 예).** 프로세스가 `L`을 쥔 채 `L`을 다시 얻는다 → `yes`. 인터럽트가 같은 CPU의 보유자를 선점해 `L`을 기다린다 → `yes`. 스레드 둘이 서로의 락을 기다린다 → `no`. 서로 다른 CPU의 처리기와 프로세스가 서로를 기다린다 → `no`.

### V7 문맥 수

질문: 교착 집합에 서로 다른 실행 문맥이 몇 개 관여하는가. 프로세스 스레드는 각각 센다. 인터럽트 처리기는 선점한 문맥과 **별개로** 센다(V6과 다른 점).

| 값 | 뜻 |
|---|---|
| `1` | 하나 |
| `2` | 둘 |
| `3plus` | 셋 이상 |
| `uncertain` | 판단할 수 없다 |

**경계 예(구성한 예).** 프로세스 하나와 그것을 선점한 처리기 → V7은 `2`, V6은 `yes`. 스레드 둘 → `2`. 스레드 둘과 처리기 → `3plus`. E2의 `Number of contexts`열은 코딩하는 동안 보지 않으며 이 값과 같다고 가정하지 않는다(`analysis/rq5/README.md`). 대응은 분석 시점에 대조한다.

### V8 고전 모델로 설명됨

질문: 고전 모델(자율 요청 + 상태 수준의 순환 대기)이 이 교착을 설명하는가. 여기서 고전 모델은 이 저장소의 SM v0.1 수준으로 좁게 읽는다: 배타적 단위 락, 요청은 각 흐름 자신의 실행에서 나옴(모델 명세 §2–§3, 가정 A4). 자기 대기는 고전 교재가 교착으로 세는지 확인하지 못했고(원문 F1, F2 미확인. 모델 명세 §3.4의 D2는 잠정) 그래서 설명되는 방식을 둘로 나눠 적는다. 둘 중 무엇을 'P_classic'으로 부를지는 사람이 정한다(열린 항목 O5-9).

| 값 | 뜻 |
|---|---|
| `classic2` | 서로 다른 둘 이상의 흐름이 각자 락을 쥔 채 다른 흐름이 쥔 락을 기다리는 순환이고(길이 2 이상) 모든 요청이 각 흐름 자신의 실행에서 나온다 |
| `self_only` | 자기 대기만으로 설명된다: 한 흐름이 쥔 락을 스스로 다시 요청하고 요청은 그 흐름 자신의 실행에서 나온다. 고전 모델이 이를 교착으로 세는 경우에만(SM은 선택 조건 FD를 걸지 않을 때) 설명된다 |
| `no` | 고전 모델로 설명되지 않는다 |
| `uncertain` | 판단할 수 없다 |

**규칙.** `classic2`는 V1이 `own` 또는 `indirect_reentry`, V5가 `2` 이상, V7이 `2` 이상, V6이 `yes`가 아닐 때만 쓴다. `self_only`는 V6이 `yes`이고 V1이 `own` 또는 `indirect_reentry`일 때만 쓴다. V1이 `irq_reentry`이면 V8은 `no` 또는 `uncertain`이다(비자율 요청은 정의상 고전 모델이 표현하지 못한다. §3.1 C4). 락이 아닌 대기가 순환에 들어 있으면 `no`다. 공유 읽기-쓰기 모드나 대기열 순서가 있어야 설명되는 교착도 SM v0.1이 표현하지 못하므로(모델 명세 §2.3의 범위 밖) `no`로 두고 `note`에 쓴다. 이때 V10은 `no`로 둔다(빈자리가 비자율 요청이나 문맥 종류가 아니라 다른 곳에 있다).

**경계 예(구성한 예).** AB-BA 두 스레드 → `classic2`. 한 스레드의 이중 잠금 → `self_only`. 처리기가 보유자를 선점한 자기 교착 → `no`(V1 `irq_reentry`). 완료 신호를 기다리는 교착 → `no`. 호출 대상이 함수 포인터로 숨은 이중 잠금 → `self_only`(V1 `indirect_reentry`).

### V9 lockdep 규칙으로 설명됨

질문: 이 교착의 모양이 lockdep의 규칙(S1) 가운데 하나에 걸리는가. lockdep이 실제로 이 교착을 찾았는지가 아니라 **그 코드가 실행되었다면 규칙이 걸었을 모양인지**를 읽기로 판단한다(lockdep은 실행되지 않은 순서는 볼 수 없다, S1). 집합 값 변수다. 규칙의 정확한 문구는 lockdep 소스를 읽지 않아 설계 문서의 요약(A−)에 기대며, 세부는 원문 재확인 전이다.

| 값 | 뜻 |
|---|---|
| `cycle` | 락 클래스 사이의 의존(한 클래스를 쥔 채 다른 클래스를 얻음)에 순환이 있다 |
| `dup` | 같은 클래스의 락을 구분 표시 없이 중복해서 얻는다(재귀 교착 가능성) |
| `usage` | 사용 상태 규칙에 걸린다: 어떤 클래스가 어떤 인터럽트 문맥에서 쓰이는데 그 인터럽트가 켜진 채로도 얻어지거나, 그 문맥에서 쓰이는 락에서 켜진 채 얻어지는 락으로의 의존이 있다 |
| `no` | 세 규칙에 걸리지 않는다. 단독으로만 쓴다 |
| `uncertain` | 판단할 수 없다. 단독으로만 쓴다 |

**규칙.** `dup`이면 V4는 `yes`다(§3.1 C5). `usage`이면 V11은 보통 `yes`다(경고 W1). 락이 아닌 대기(V3의 `non_lock_wait`)는 lockdep의 락 순서·IRQ 상태 모델 밖이므로 그 대기가 교착의 핵심이면 `no`다(S38 표지 글의 서술, A−).

**경계 예(구성한 예).** 락 클래스 `A→B`와 `B→A`가 코드에 모두 있다 → `cycle`. 서브클래스 표시 없이 같은 클래스 락을 중첩한다 → `dup`. 처리기가 쓰는 락을 프로세스 문맥에서 인터럽트를 끄지 않고 얻는다 → `usage`(V11 `yes`). 중복과 사용 상태가 함께 걸린다 → `dup+usage`.

### V10 확장 모델이 필요

질문: 고전 모델도 lockdep 규칙도 이 교착을 설명하지 못하고, 비자율 요청이나 문맥 종류를 모델의 구성 요소로 두어야만 기술할 수 있는가. 'RQ5의 확장이 필요하다'는 주장의 직접 근거이므로 가장 엄격하게 쓴다.

| 값 | 뜻 |
|---|---|
| `yes` | V8이 `no`이고 V9가 `no`이며, 비자율 요청이나 문맥 종류 없이는 기술할 수 없다는 근거를 한 문장으로 적을 수 있다 |
| `no` | 위 조건이 아니다(V8이나 V9가 설명하거나, 설명되지 않아도 빈자리가 확장이 아닌 곳에 있다. 예: 락이 아닌 대기) |
| `uncertain` | 판단할 수 없다 |

**규칙.** `yes`이면 `V10_reason`에 근거 한 문장을 적는다(비어 있으면 도구가 거부한다). V8과 V9가 둘 다 정확히 `no`가 아니면(`uncertain` 포함) `yes`를 쓸 수 없다(§3.1 C1). `yes`는 V1이 `irq_reentry`나 `other`이거나 V2에 프로세스 밖 문맥이 있을 때만 쓴다(C1b). 근거 문장의 형식은 "이 교착은 <처리기·문맥>이 <락>을 쥔 <문맥>을 선점해 요청을 삽입한다는 점에 의존하고, 자율 요청의 대기 관계로는 보유자가 왜 해제하지 못하는지 기술할 수 없으며, lockdep의 세 규칙에는 해당하지 않는다"처럼 세 가지를 모두 말한다.

`yes`가 가능한 사례가 실제로 있는지는 모른다. 도구의 시험은 구성한 행으로 규칙을 시험했을 뿐이다. 모든 값이 `no`이고 V10도 `no`이면 어느 설명도 아닌 사례다(A1의 P_none).

### V11 인터럽트를 켠 채 락을 쥔 구간

질문: 교착에 관여한 락이, 그 락을 쓰는 인터럽트가 켜진 채로 얻어지는가. lockdep의 '켜진 채 획득' 사용 정보에 대응한다(S1). 락 클래스의 사용 상태이며 V12와 다르다(아래 상자).

| 값 | 뜻 |
|---|---|
| `yes` | 켜진 채 쥐는 구간이 있다 |
| `no` | 없다(인터럽트를 끄고 쥔다) |
| `uncertain` | 판단할 수 없다 |

수정이 락 획득을 인터럽트를 끄는 변형(예: `…_irqsave`류)으로 바꾸는 것이면 수정 전에 켜진 채 쥐었다는 근거가 된다. 코딩 때 이 단서를 `evidence`에 적는다.

> **'인터럽트 의존'의 두 의미를 섞지 않는다.** V11은 락 클래스의 사용 상태(S1, 정점의 속성)이고 V12는 의존 간선의 종류(S35)다. 하나는 정점의 속성이고 다른 하나는 간선의 종류라 층위가 다르다. 둘을 섞어 읽으면 5e와 5f의 판정이 달라진다(문서 05 §6).

### V12 의존의 종류(S35)

질문: 교착을 이루는 의존 간선이 어떤 종류인가. S35의 인터럽트 인식 락 그래프는 일반 간선과 인터럽트 간선을 두고 인터럽트 간선이 하나 이상 든 순환을 교착 후보로 본다(문서 05 §6.2, A−). 락 그래프에 그릴 수 있는 의존만 가른다.

| 값 | 뜻 |
|---|---|
| `general` | 모든 의존이 일반 의존(락을 쥔 채 다른 락을 얻음)이다 |
| `interrupt` | 의존 하나 이상이 인터럽트 의존이다(처리기가 락을 쥔 문맥을 선점해 락을 얻어 생긴 의존) |
| `na` | 락 의존 그래프로 그릴 수 없는 대기이거나 종류를 나눌 의미가 없다(예: 락이 아닌 대기) |
| `uncertain` | 판단할 수 없다 |

**우선순위.** `interrupt` > `general` > `na`. V1이 `irq_reentry`이면 정의상 V12는 `interrupt`다(경고 W5). 반대로 V12가 `interrupt`인데 V1이 `irq_reentry`가 아니면 이유를 `note`에 적는다(경고 W2).

**경계 예(구성한 예).** 처리기가 락 `L1`을 쥔 문맥을 선점해 `L2`를 얻고 다른 흐름이 `L2`를 쥔 채 `L1`을 기다린다 → `interrupt`. 스레드 둘의 AB-BA → `general`. 완료 신호 대기 → `na`.

### V13 락 오용 범주(M106)

질문: M106이 락 오용 사례를 나눈 다섯 범주 가운데 이 교착의 오용 모양은 어느 것인가. 재분류 결과를 M106의 분류와 대조하려는 교차 열이다(문서 02 §5.4의 G4 반영 (c)). 범주 이름은 대장(C-SUR-177)이 옮긴 한국어 이름에서 가져왔고 원문의 영어 이름과 정의는 확인하지 못했다(열린 항목 O5-7). 아래 정의는 이 코드북의 작업 정의다. M106에서 인터럽트는 범주가 아니다(문서 05 §6.2).

| 값 | M106 범주(대장의 이름) | 작업 정의 |
|---|---|---|
| `circular_acq` | 순환 획득 | 락들이 서로 반대 순서로 얻어져 순환이 생긴다 |
| `double_lock` | 이중 잠금 | 이미 쥔 락을 풀지 않고 다시 얻는다 |
| `missing_unlock` | 해제 누락 | 어떤 경로에서 쥔 락을 풀지 않아 뒤의 획득이 영원히 기다린다 |
| `release_unacquired` | 획득하지 않은 락 해제 | 쥐지 않은 락을 푼다 |
| `uninit_lock_use` | 미초기화 락 사용 | 초기화되지 않은 락을 쓴다 |
| `na` | | 다섯 범주 어디에도 맞지 않는다(락이 아닌 대기, 인터럽트 선점에 의존하는 모양 등) |
| `uncertain` | | 판단할 수 없다 |

범주가 여럿 겹치면 교착을 직접 만든 것을 고르고 나머지는 `note`에 적는다. 이중 잠금이면 V6이 `yes`여야 한다(경고 W4).

## 3. 변수 사이의 규칙, 불확실 처리

### 3.1 모순 규칙과 경고

`codebook_tools.py`의 `validate`가 코딩 표 한 행마다 검사한다. 오류는 코딩이 코드북과 어긋난다는 뜻이고 경고는 드물지만 가능한 조합이다. 규칙을 통과해도 코딩이 맞다는 뜻은 아니다.

| 규칙 | 내용 | 근거 |
|---|---|---|
| C1 | V10이 `yes`이면 V8과 V9가 모두 정확히 `no`다 | V10의 정의 |
| C1b | V10이 `yes`이면 V1이 `irq_reentry`나 `other`이거나 V2에 `hardirq`, `softirq`, `threaded_handler`가 있다 | 확장이 필요한 이유가 비자율 요청이나 문맥 종류여야 함 |
| C2 | V8이 `classic2`이면 V1은 `own` 또는 `indirect_reentry`, V7과 V5는 `2` 이상, V6은 `yes`가 아니다 | 고전 순환 대기의 정의 |
| C3 | V8이 `self_only`이면 V6은 `yes`, V1은 `own` 또는 `indirect_reentry`다 | 자기 대기의 정의 |
| C4 | V1이 `irq_reentry`이면 V8은 `no` 또는 `uncertain`이다 | 비자율 요청은 고전 모델 밖 |
| C5 | V9에 `dup`이 있으면 V4는 `yes`다 | 중복 획득은 같은 클래스 중첩 |
| W1 | V9에 `usage`가 있는데 V11이 `yes`가 아니다 | 사용 상태 규칙은 켜진 채 획득을 전제 |
| W2 | V12가 `interrupt`인데 V1이 `irq_reentry`가 아니다 | 인터럽트 의존은 보통 선점에서 생김 |
| W3 | V3에 `non_lock_wait`가 있는데 V8이 `classic2`나 `self_only`다 | 락이 아닌 대기는 SM 범위 밖 |
| W4 | V13이 `double_lock`인데 V6이 `yes`가 아니다 | 이중 잠금은 보통 자기 대기 |
| W5 | V1이 `irq_reentry`인데 V12가 `interrupt`나 `uncertain`이 아니다 | 선점한 처리기의 요청은 정의상 인터럽트 의존 |

형식 오류(`E-field`, `E-type`, `E-value`, `E-unc`, `E-evid`, `E-dup`)는 열이 없거나 남는 경우, 해시·정수 형식, 값 집합 밖의 값, `uncertain`인데 사유가 없음, 근거가 없음, 같은 (커밋, 코더, 회차)의 중복이다. (V1, V6, V8) 조합 가운데 허용되는 것은 `formal/rq5/codebook-tools-check.md` §1의 표에 있다.

### 3.2 파생 규칙이 아닌 것

규칙은 한 방향의 필요조건만 검사한다. 예를 들어 V8이 `classic2`일 때 V9가 무엇이어야 하는지는 정하지 않는다. 락 순서가 뒤집힌 고전 순환은 보통 V9의 `cycle`에도 걸리지만, 그런 사례가 `no`로 코딩되는 이유가 있을 수 있으므로(예: 두 경로가 같은 락 클래스를 쓰지 않음) 도구가 막지 않는다.

### 3.3 불확실 처리

모든 변수에 `uncertain`이 있다. 값 대신 `uncertain`을 쓰면 `unc_reason`에 사유를 적어야 한다(도구가 거부한다).

| 사유 | 뜻 | 후속 |
|---|---|---|
| `U1` | 정보 부족: 메시지·패치·링크된 논의에 판단 근거가 없다 | 정보원을 더할 수 있으면 더하고(`ml`, `other`) 그래도 없으면 `uncertain`으로 확정 |
| `U2` | 커널 지식 필요: 문맥이나 락의 성질을 읽는 쪽이 확신하지 못한다 | `status`를 `needs_expert`로 둔다 |
| `U3` | 정의 모호: 코드북의 경계가 이 사례를 가르지 못한다 | 코드북 정의 수정 후보로 모은다(prereg §8의 허용 변경 절차) |

여러 사유는 작은 번호부터 `+`로 잇는다(예: `U1+U2`). 도구는 사유가 목록 안의 값인지만 본다. `uncertain`은 분석에서 두 가지로 따로 보고한다: (i) 설명 안 됨으로 센 값(설명 비율의 하한), (ii) 분모에서 뺀 값(prereg §5 A1). 불확실 비율이 25%(계획용)를 넘어 판정이 처리 방식에 따라 뒤집히면 '판정 불가'로 보고한다(prereg §7).

## 4. 분석 변수와 코드북 값의 대응

prereg §5의 양을 코드북 값으로 풀어 쓴다. 이 대응을 결과를 보기 전에 고정하려는 것이다.

| 양 | 정의 |
|---|---|
| P_classic | O5-9의 결정에 따라 V8이 `classic2`(좁게) 또는 `classic2` 또는 `self_only`(넓게). 두 가지를 모두 보고하되 어느 쪽이 주 지표인지는 사전에 고정한다 |
| P_lockdep | V9가 `no`도 `uncertain`도 아니다(규칙 유형이 하나 이상) |
| P_union | P_classic과 P_lockdep 가운데 하나라도 참. 둘 다 거짓이면 거짓, 그 밖(한쪽이 `uncertain`이고 다른 쪽이 거짓)은 불확실 |
| P_ext | V10이 `yes` |
| P_none | V8이 `no`, V9가 `no`, V10이 `no` |
| 자기 대기 비율(A2) | V6이 `yes` |
| 인터럽트 재진입 수 x(A3) | E2의 정의로 단일 스레드인 사례 가운데 V1이 `irq_reentry`인 수. 단일 스레드 판정은 분석 시점에 E2 열에서 대조 |
| 교차(A4) | V1×V8, V1×V9, V12×V9, V13×V10. 기술 통계만 |

## 5. 파일럿과 일치도

절차는 prereg §4의 것이다. 이 절은 도구가 구현한 방식을 적는다.

1. **합격선과 임계값을 사람이 고정한다**: κ 합격선 0.61, 재파일럿 규칙, x_min = 5, 자기 대기 10%, '대부분' 0.70, 불확실 25%(모두 계획용 값. O5-2, O5-3). 파일럿 전에 고정한다. 본 코딩 뒤에는 바꾸지 않는다(prereg §8).
2. **파일럿 표본을 뽑는다.** `codebook_tools.py pilot index.csv 1`이 49건의 해시에서 10건을 단순 무작위 비복원으로 뽑는다. 시드는 마스터 이름 `rq5-pilot`과 회차에서 SHA-256으로 정하고 입력 순서와 무관하다. 회차 2는 회차 1의 사례를 뺀 나머지에서 뽑는다. **아직 뽑지 않았다**: 위 1이 끝나기 전에는 뽑지 않는다.
3. **두 코더가 서로의 코딩을 보지 않고 코딩한다.** 코더 1은 사람, 코더 2는 AI다. 코딩 표는 `validate`로 검사한다.
4. **일치도를 계산한다.** `codebook_tools.py agree <코더1 파일> <코더2 파일>`이 핵심 변수 V1, V2, V6, V8, V9, V10에 대해 변수마다 일치율, Cohen의 κ, 사례 복원 추출 부트스트랩 95% 구간(2000회, 시드 결정적)을 낸다. 합격 여부(κ ≥ 합격선)는 표시만 하고 확정은 사람이 한다.
5. **합격선에 못 미친 변수는 정의를 고쳐 다른 10건으로 한 번 더 파일럿한다**(`pilot2`). 두 번째에도 못 미치면 그 변수는 기술 통계로만 쓰고 그 변수에 의존하는 판정은 '판정 불가'로 보고한다(prereg §4).
6. **본 코딩.** 49건을 두 코더가 독립 코딩하고 κ를 49건 전체에서 보고한다. 불일치는 토의로 해소하고 해소되지 않는 것은 사람이 최종 판정한다.

**집합 값 변수의 일치 단위.** V2, V9는 핵심 변수이고 집합 값이다. 도구의 기본은 **값 문자열 전체**(정렬된 집합)를 하나의 범주로 보는 것이다. 부분만 겹쳐도 불일치로 센다. 이는 엄격하다. 보조로 원소마다 '값에 들어 있는가'의 이진 κ를 낸다(합격 판정에는 쓰지 않음). 어느 단위를 합격 판정에 쓸지는 사람이 정한다(열린 항목 O5-10).

**κ가 정의되지 않는 경우.** 두 코더가 파일럿에서 한 변수에 같은 한 범주만 썼으면 기대 일치도가 1이어서 κ가 정의되지 않는다. 도구는 `undefined_agree`(일치율 1)와 `undefined_disagree`(일치율 < 1)로 표시하고 합격이나 불합격으로 세지 않는다. 그 변수를 파일럿이 시험하지 못한 것으로 보고 어떻게 처리할지는 사람이 정한다(열린 항목 O5-11).

**한계.** 사례가 10건이면 κ는 불안정하고 구간이 넓다. 드문 값은 파일럿에 나오지 않을 수 있다. 합격선은 점추정값에 적용한다(prereg §4). 이것은 일치도를 재는 방법의 한계이며 코드북이 옳다는 증거가 아니다.

## 6. 도구 사용

```
python3 -I analysis/rq5/codebook_tools.py template                    # 코딩 표 머리글(23열)
python3 -I analysis/rq5/codebook_tools.py validate <코딩 파일>        # 값·모순 검사. 오류가 있으면 종료 코드 1
python3 -I analysis/rq5/codebook_tools.py pilot analysis/rq5/index.csv [1|2]
python3 -I analysis/rq5/codebook_tools.py agree <코더1 파일> <코더2 파일>
python3 -I analysis/rq5/check_codebook_tools.py formal/rq5/codebook-tools-check.md   # 도구 자체 시험
```

코딩 표는 23열이다: 식별 6열(`e2_row`, `commit`, `coder`, `round`, `status`, `sources`), 변수 13열(`V1`–`V13`), 부가 4열(`V10_reason`, `unc_reason`, `evidence`, `note`). 코딩 표에는 커밋 해시와 이 연구의 자체 코딩만 둔다. E2의 원본 표를 복제하지 않는다(LICENSE 없음, prereg §4).

## 7. prereg/RQ5 §4와의 차이 (제안)

사람이 승인하기 전에는 prereg의 표가 정본이다. 승인되면 prereg를 v0.2로 고치고 이 표를 정본으로 옮긴다(열린 항목 O5-12).

| 번호 | prereg v0.1 | 이 코드북 v0.1 | 이유 |
|---|---|---|---|
| a | V8: 예/아니오 | `classic2`, `self_only`, `no`, `uncertain` | 자기 대기를 교착으로 세는지 확인하지 못해(F1, F2 미확인, D2 잠정) 어느 읽기로도 재코딩 없이 분석하게 함. 대가: P_classic의 정의를 사람이 정해야 함(O5-9) |
| b | V3: 스핀락/뮤텍스/rwsem·rwlock/세마포어/기타 | `기타`를 `other_lock`과 `non_lock_wait`로 나눔 | 락이 아닌 대기는 SM 범위 밖이고 별도 도구가 대상으로 삼음. 하나로 두면 W3·V9 규칙을 적용하기 어려움 |
| c | V2, V3, V9: 값 하나 | 집합 값(사전순 `+`) | 한 사례에 문맥·락 종류·규칙 유형이 여럿 관여할 수 있음. 대가: κ의 단위(O5-10) |
| d | V1: 우선순위 없음 | `irq_reentry` > `other` > `indirect_reentry` > `own`, 재개 불가 시험 | 같은 사례를 코더가 다르게 읽는 일을 줄임 |
| e | V5, V7: 코딩자의 판단 | 락 객체 수, 처리기를 별개로 센 문맥 수로 정의 | V6(처리기를 세지 않음)과의 차이를 분명히 함 |
| f | 값마다 '불확실' | 불확실 사유 `U1`–`U3` | 불확실의 원인별 후속 처리를 정하기 위함 |
| g | (없음) | 코딩하는 동안 E2 열을 보지 않음 | 교차 분석의 독립성 |
| h | (없음) | 모순 규칙 C1–C5, C1b, 경고 W1–W5, 도구 검증 | 형식 오류와 모순을 코딩 단계에서 거름 |
| i | V12/V13: 값 | V12: `general`, `interrupt`, `na`, `uncertain`. V13: M106 다섯 범주 이름(`circular_acq` 등)과 `na`, `uncertain` | 값 이름을 정함. 범주 이름은 대장의 한국어 이름에서 옮김(O5-7) |
| j | V8의 '고전 모델': 자율 요청 + 상태 수준 순환 대기 | SM v0.1 수준(배타적 단위 락, 자율 요청)으로 좁게 읽음. 공유 모드·대기열 순서·신호 대기가 필요하면 `no` | 코더마다 '교재의 고전 모델'을 넓게 읽어 갈리는 일을 막음. 대가: V8의 `classic2` 비율이 교재 일반의 능력보다 작게 나올 수 있음(§9) |

## 8. 열린 항목 (사람이 정해야 함)

prereg §9의 O5-1–O5-8(코더 구성, κ 합격선, 임계값, 커밋을 읽는 경로, 저자 문의, 원문, M106 범주, 모델 명세 D2·D5)에 이 코드북이 다음을 더한다. 파일럿 전에 정해야 한다.

| 번호 | 항목 | 제안 |
|---|---|---|
| O5-9 | V8의 두 값 가운데 무엇을 P_classic으로 부르는가 | 주 지표는 좁게(`classic2`만). 이유: 고전 교재의 자기 대기 취급을 확인하지 못했다. 넓게(`classic2` 또는 `self_only`)도 같이 보고 |
| O5-10 | 집합 값 변수(V2, V9)의 κ 단위 | 합격 판정은 값 전체 일치. 원소별 κ는 기술용 |
| O5-11 | κ가 정의되지 않는 변수의 처리 | 합격이나 불합격으로 세지 않고 '파일럿에서 시험하지 못함'으로 보고. 그 변수는 본 코딩 κ로 확인하되 합격선 적용은 사람이 정함 |
| O5-12 | 이 코드북의 승인과 prereg 변경(§7의 a–j), 코딩 중 E2 열을 보지 않는 규칙 | 승인 뒤 prereg를 v0.2로 고침 |

참고: O5-4(커밋을 읽는 경로)는 시험하지 않았다. 작업공간에서 공개 저장소를 부분 복제하려면 저장소 추가와 내려받기 허락이 필요하고, 사례 코딩은 동결 뒤 일이기도 하다.

## 9. 한계

- 사례를 하나도 읽지 않고 쓴 정의다. 실제 사례가 두 값 사이에 걸치는 방식은 파일럿에서 처음 드러난다. `U3`가 많이 나오면 정의가 사례를 가르지 못하는 것이다.
- 커널 성질(문맥 종류, 락의 인터럽트 사용 상태, 폴트 진입의 분류)에 대한 서술은 전문가 확인 전이다.
- 문헌 근거(S1, S35, S38, T13, M106)는 대부분 열람 도구 요약이나 초록이다. lockdep 소스, M106 원문, F1·F2 원문을 읽지 않았다.
- 읽기 기반 코딩이다. 커널을 실행하지 않았고 '설명됨'은 실행으로 확인한 것이 아니다.
- V8의 '고전 모델'을 SM v0.1 수준으로 좁게 읽었다(§7의 j). 교재의 고전 모델이 공유 모드나 신호 대기를 포함해 설명하는 사례도 `no`가 되므로 `classic2`의 비율은 교재 일반의 설명력보다 작을 수 있다.
- 코더 2가 AI이고 이 코드북도 AI가 썼다. 일치도가 높게 나와도 독립적인 확인이 아니다.
- 표본은 mainline 수정 커밋에서 키워드로 거른 49건이다. 수정된 버그만 있으므로(생존 편향) 이 코딩 결과를 커널 교착 일반으로 옮기지 않는다.
