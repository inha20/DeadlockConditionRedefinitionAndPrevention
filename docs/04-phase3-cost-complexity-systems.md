## 2. 정규화: 변수, 단위, 정보 수준

### 2.1 기호 표

| 기호 | 뜻 | 문헌별 표기와 충돌 |
|---|---|---|
| n | 프로세스(스레드, 트랜잭션) 수 | 뱅커 문헌 공통 |
| m | 자원 종류 수 | Belik(M6)은 m. Lee·Mooney 학위논문 초록은 DDU 비용을 O(min(m,n))로 쓰며 m을 자원 수, n을 프로세스 수라 한다(S20) |
| d | 자원 종류 수 | Zohora 외(S13), Li(M27, M28)는 d |
| M | 모든 종류의 자원 단위 총수 | Li(M27)만 씀 |
| 정점 수, 간선 수 | 증분 순환 탐지 문헌(G1~G3)은 각각 n, m으로 쓴다 | **뱅커 문헌의 (n, m)과 뜻이 다르다.** 비용을 합칠 때 반드시 기호를 바꿔 쓴다 |
| K0~K3 | 정보 수준(문서 02 §4: 현재 상태만 / 최대 요구 선언 / 락 클래스 순서·의존 / 프로그램 전체) | 본 계획의 작업 가설 |

### 2.2 단위 비용

- 교재식 안전성 검사는 최대 n번의 반복마다 n개 프로세스를 훑고 한 번의 비교가 m차원 벡터 비교라서 n·n·m, 곧 Θ(mn²)이다(M6 초록 B. 교재 서술은 C).
- Zohora 외(S13)의 "비교 횟수"가 스칼라 비교인지 벡터 비교인지는 열람한 본문에서 불분명하다. 같은 알고리즘의 단위 비용이 d배 달라질 수 있다.
- **제안(WP6.2에서 확정)**: 비용의 기본 단위는 스칼라 비교 1회로 하고, 벡터 비교 횟수는 따로 보고한다. 변수는 문서 02 SI-1의 기호(n, m)로 통일하고 인용문의 d는 m으로 옮겨 적되 원문 기호를 병기한다.

### 2.3 O(n³d) 표기의 출처 후보

문서 02 §5.1이 "한 학술 사이트의 글"(P14, C)로만 알던 O(n³d)에 1차 출처 후보가 생겼다. Li(M27) 초록이 원래 알고리즘의 시간을 O(n³d)로 쓰고, 일부 문헌의 Θ(n²d)는 안전성 검사 부분만을 가리키는 오인용이라고 설명한다(B, 초록만). O(n³d)가 무엇을 센 값인지(요청 하나의 처리인지 전체 시퀀스인지)는 본문을 읽어야 안다. 이 불일치를 오류로 단정하지 않는다.

### 읽는 법

1. **같은 안전성 문제가 모델 변수 하나로 갈린다.** 뱅커는 미래 정보를 '최대 청구'(K1)로 압축해 다항이 되고, 다단계 획득 구조(K3)에서는 NP-완전이 된다(M9). 락 프로그램의 정적 분석은 중첩 여부로 결정 가능성이 갈린다(M38).
2. **열쇠는 '교착 없는 불안전 상태'의 존재 여부다.** 그런 상태가 없는 구조에서는 안전성이 현재 상태의 교착 탐지로 환원된다(M9 Prop. 2, §5). SM의 관찰 O1(뱅커 안전 ⟺ s_max 상태에 교착 집합 없음)과 같은 모양이다(V).
3. **다항이라는 것과 커널에서 쓸 만하다는 것은 다르다.** 이 표는 점근 서술이며 실제 락 획득당 비용은 §3에서 X다.
4. **RQ2에 미치는 영향**: M9가 제조 시스템 맥락에서 구조 조건 아래 다항 클래스를 이미 주고, M38이 중첩 락 클래스의 결정 가능성을 이미 다룬다. 독자적일 수 있는 부분은 OS의 구조 제한(락 중첩 깊이, 인터럽트 문맥)으로 정의한 클래스 중 위 결과가 덮지 않는 부분뿐이다. G4에서 '부분'일 가능성이 높다(해석).

Go 연구(E5)는 이 문서를 처음 쓸 때 블로그 요약으로만 확인했고, 2026-10-31에 본문을 읽었다(A−, 열람 도구 요약 경유, 대장 C-SUR-080). 블로킹 버그 85건(전체 171건 중) 가운데 Mutex 관련이 28건, RWMutex 관련이 5건이다(Table 6). 본문은 Mutex 28건의 원인에 이중 락, 잠금 순서 충돌, 해제 누락이 있다고 쓰지만 유형별 건수를 주지 않으므로 이 연구로는 이중 락 비중을 계산할 수 없다. 그래서 위 표에 E5 행을 넣지 않았다. 이전 열람에서 기록했던 'Mutex 관련 28건'은 Table 6으로 확인되었다.

**읽는 법과 한계**

1. 분모가 다르다. '단일 스레드 교착'(E1, E2)은 이중 락과 같지 않다. E2의 단일 문맥 교착 16건 중 동기화 오용 열이 빈 값인 것이 8건이고 mutex 6건, spinlock 1건, workqueue 1건이다(문서 03 §3.3). Rust 연구들은 이중 락을 직접 센다. 그러므로 22.6%~78.9%를 한 척도로 읽으면 안 된다.
2. 표본의 성격이 다르다. 전부 수정된 버그만 보는 키워드 표본이다(생존 편향). E3는 Servo, TiKV, Rand 세 응용, E4는 더 넓은 Rust 프로젝트와 CVE·RustSec, E1은 MySQL, Apache, Mozilla, OpenOffice, E2는 리눅스 커널이다. 언어와 시기가 다르다.
3. E3의 표 4는 'Mutex' 열을 7로 적고 본문이 이를 이중 락이라 부르며 그림은 RwLock 예다. Mutex와 RwLock의 분리는 없다.
4. 원인 해석은 하지 않는다. 같은 수치가 언어의 수명 규칙, 코드 스타일, 수정 커밋 선별 방식 중 무엇 때문인지 이 자료로는 알 수 없다.

**H5a에 대한 의미**: "자기 대기가 조건 모델이 무시할 수 없는 비중"이라는 동기는 모든 표본에서 지지된다(최소 22.6%). 다만 '지지'는 동기의 근거일 뿐이고 RQ5의 사례 코딩(E2 49건)이 같은 질문을 다시 직접 답한다. 반증 조건은 RQ5 사전 등록 때 정한다(문서 03 §7의 H5b 규칙과 같은 방식). 다중 인스턴스 자원이 관여하는 교착의 비율은 여전히 미확인이다.

## 11. G3 판정, 설계 영향, 일정 재추정

### 11.1 판정

**조건부 통과.** 조건은 §0에 있다. 통과를 막는 것은 없고, 모든 X 칸은 원문 확보 또는 RQ3 측정으로 채울 수 있는 종류다.

### 11.2 연구 설계에 미치는 영향

1. **RQ6**: 인벤토리에서 의사코드 수준의 재구현을 본문으로 확인한 것은 R6-06, R6-07 두 건이다. 문서 02 §5.1의 중단 규칙에 따라 최소 건수(제안 4건)를 사전 분석 계획에 기록해야 하고, 못 채우면 인벤토리 범위를 넓히거나 문헌 비교로 축소한다. 핵심 재현 대상은 DBDAA(R6-07)이며 정확성 시험으로 R6-05도 다룰 가치가 있다. R6-07은 R6-05로 보이는 방법(Begum 외로 인용. 같은 논문인지는 저자명으로 한 추정이다)이 자기 데이터셋에서 '불안전'이라 판정한 것을 오류라고 서술한다.
2. **RQ2**: 중복 위험이 높다(§4 읽는 법 4). G4에서 '부분'을 예상한다.
3. **RQ4**: 증분 순환 탐지의 교착 응용이 문헌에 이미 있다(G2 서론, M7, S10(C)). 중복 위험 '높음'을 유지하고 G4에서 '동일'이면 RQ3의 P-INC 항목으로 흡수한다.
4. **RQ5**: H5a의 동기는 지지된다(§6). 함께 검토할 질문 하나를 추가한다: 자기 대기를 조건 모델의 일부로 둘지, 락 타입의 계약(§5)으로 볼지.
5. **RQ3**: 비용표의 수치 칸이 대부분 X라서 측정의 정보 가치가 높다. 뱅커 비용은 변수·단위를 먼저 고정해야 한다(§2.2).
6. **RQ1과 SI-1**: 문서 01 §1.2의 AND·OR 행 정정(v0.3)이 명세 §7의 모델 매트릭스와 일치한다. 명세에 복잡도 표기 규약(§2.1)을 넣는 일을 다음 개정(v0.2)으로 미룬다.

### 11.3 일정 재추정

- 문서 03 §8과 같은 이유로 사람의 시간에 대한 1.5배 규칙은 적용하지 않는다. 이번 작업은 AI가 작업 세션 안에서 수행했으며 병목은 원문 확보와 사람의 검토다.
