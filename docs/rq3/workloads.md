## 1. 생성기가 정책에 넘기는 것

`Workload(name, nlocks, threads, params)`는 스레드마다 `Task`의 튜플을 가진다. `Task`는 직선 락 프로그램 `ops`(`('A', l)`, `('R', l)`의 열; `docs/rq3/policies.md` §1의 모델)와, 연산 뒤에 쓰는 시간 `work`(`ops`와 같은 길이)다. 획득 뒤의 `work`는 그 락을 쥔 채 하는 일의 길이이고, 반납 뒤의 값은 0이다.

락 표(`LockTable`)와 소규모 전수 검사는 스레드마다 프로그램 하나를 받는다. `Workload.first_programs()`가 스레드마다 첫 작업의 프로그램을 돌려준다. 스레드가 작업을 여러 개 이어서 실행하는 경우(`tasks_per_thread` > 1)는 생성기가 만들 수 있지만 지금의 실행기가 다루지 않는다(시간 모델이 필요한 부분, §6).

## 2. L1 합성 워크로드

### 2.1 매개변수

| 이름 | 계획값 | 뜻 |
|---|---|---|
| `T` | 16 | 스레드 수 |
| `R` | 32 | 락 수. 이 모델에서 락 하나가 락 클래스 하나다(`policies.md` §1) |
| `zipf_s` | 0, 0.8, 1.2 | 락 선택의 Zipf 지수. 경쟁 수준의 정의: 낮음 0, 중간 0.8, 높음 1.2 |
| `depth` | 1, 2, 4 | 작업이 동시에 쥐는 락 수(중첩 깊이 d) |
| `p_viol` | 0, 0.05, 0.25 | 작업의 락 획득 순서가 전역 클래스 순서(락 번호 오름차순)와 어긋날 확률 p_v |
| `rho_rb` | 1, 10 | 롤백 비용 계수. **생성기는 값을 싣기만 하고 쓰지 않는다**(시뮬레이터의 몫) |
| `cs_dist`, `cs_mean` | 지수·로그정규, 평균 1 | 임계구역 길이의 분포(로그정규의 시그마는 1). `work`에 값을 쓴다 |
| `tasks_per_thread` | 1 | 스레드당 작업 수 |
| `hot_random` | 참 | 인기 순위와 락 번호의 대응을 인스턴스마다 무작위로 섞는다(O3-19) |

값은 `prereg/RQ3.md` §4.4의 계획용 값이고 동결 때 확정한다.

### 2.2 작업 생성 절차

작업 하나를 만드는 절차는 다음과 같다(코드: `bench/workloads/l1.py`의 `make_l1`).

1. 인기 순위 r(0..R−1)의 가중치를 w_r ∝ 1/(r+1)^s로 둔다(s = 0이면 균등).
2. 순위를 가중치에 비례해 **복원 없이** d개 뽑는다(한 개를 뽑고, 뽑힌 순위를 빼고 남은 가중치를 다시 정규화하는 순차 추출). 한 작업 안의 락은 항상 서로 다르다.
3. 순위를 락 번호로 바꾸는 대응은 인스턴스마다 무작위 순열이다(`hot_random`). 대응이 항등이면 인기 있는 락이 번호가 낮은 쪽에 몰려, 경쟁과 순서 위반이 한 요인으로 섞인다(O3-19).
4. 락 번호를 오름차순으로 정렬한다. 이것이 전역 클래스 순서를 따르는 획득 순서다.
5. 깊이가 2 이상이면 확률 p_v로 순서를 위반한다: 정렬 순서가 아닌 무작위 순열로 바꾼다(깊이 2에서는 뒤집기뿐이다).
6. 프로그램은 정한 순서로 획득하고 획득의 역순으로 반납한다(중첩). 획득마다 임계구역 길이를 뽑아 `work`에 쓴다.

생성은 (마스터 시드, 매개변수, 인스턴스 번호)에서 결정적이다(`bench/seeds.py`의 파생 규칙). 같은 입력은 같은 워크로드를, 다른 인스턴스 번호는 다른 워크로드를 낳는다(점검 A1).

### 2.3 알아 둘 점

- 복원 없이 뽑으므로 한 작업에 한 락이 두 번 들어가지 않는 대신, 락이 작업에 들어갈 확률은 가중치의 d배와 같지 않고 그보다 작다(가중치가 큰 락일수록 차이가 크다). 경쟁 수준의 라벨(낮음·중간·높음)은 Zipf 지수 값으로 정의한 것이고, 실제 충돌 비율은 결과로 따로 보고해 점검한다(`prereg/RQ3.md` §4.4).
- 깊이 1에서는 순서 위반이 정의되지 않으므로 p_v는 영향이 없다. 핵심 격자 27셀 가운데 깊이 1의 9셀은 같은 분포를 세 번 만든다(O3-22).
- p_v는 '작업 단위'로 정의했다: 작업이 정렬 순서가 아니게 락을 얻는 확률이다. 깊이가 4일 때 한 작업 안에서 어긋난 쌍의 비율이 아니다(O3-23).
- `rho_rb`와 임계구역 길이는 시간 모델이 있어야 의미를 가진다. 현재의 무작위 스케줄 실행기는 이 값들을 쓰지 않는다.

### 2.4 핵심 격자와 스윕

핵심 격자는 Zipf 지수 3 × 깊이 3 × p_v 3 = 27셀이고 T = 16, R = 32, 지수 분포, ρ_rb = 1이다. T, R, 분포, ρ_rb는 중심 셀(중간 경쟁 0.8, 깊이 2, p_v = 0.05) 주변에서 한 번에 하나씩 바꾼다(일차원 스윕). 스윕은 아직 실행하지 않았다.

## 3. L2 고전 문제

- **식사하는 철학자**(`dining_philosophers(n, asymmetric)`): 포크 i는 락 i. 철학자 i는 포크 i를 얻고 포크 (i+1) mod n을 얻는다. 변형(`asymmetric`)은 마지막 철학자만 두 포크의 순서를 뒤집는다(교착을 피하는 고전적 방법의 하나). 일반형은 마지막 철학자가 포크 n−1을 얻은 뒤 포크 0을 요청하므로 락 번호 순서를 어기고, 이것이 순환 대기를 만든다.
- **계좌 이체**(`account_transfer(T, accounts)`): 스레드마다 서로 다른 두 계좌를 골라 (보내는 쪽, 받는 쪽) 순서로 락을 얻는다. 락 번호 순서와 무관한 순서이므로 순서 위반이 흔하다.

n, 계좌 수, 스레드 수는 열린 항목이다(O3-24).

## 4. 무작위 스케줄 실행기

`bench/lockrun.py`의 `run_random(progs, pol, seed, nlocks, ...)`은 같은 정책 코드(`bench/policies/lock/`)를 락 표 위에서 돌린다. 매 걸음 실행 가능한 스레드 하나를 균등하게 골라 진행한다(탐지 정책은 탐지 동작도 후보에 넣는다). **시간 모델이 없다.** 걸음은 논리 순서일 뿐 시간이 아니다.

용도는 두 가지다. (1) 소규모 전수 검사(`bench/lockexplore.py`)가 닿지 않는 크기(T = 16, R = 32)에서 같은 코드의 구현 무결성을 점검한다: 걸음마다 정책 불변식과 교착 집합(모델 명세 §3.1)을 검사한다. (2) 합성 트레이스(`traces/FORMAT.md`)를 만든다. 정책의 순위, 비용, 완료 시간에 대해서는 아무것도 말하지 않는다.

## 5. 합성 트레이스와 도구

- 형식: `traces/FORMAT.md`(`rq3-trace-v0.1`, JSON Lines). 머리 레코드 하나와 이벤트(`BEGIN`, `REQUEST`, `WAIT`, `ACQUIRE`, `RELEASE`, `ABORT`, `FAIL`, `END`).
- 견본: `python3 -I traces/make_samples.py`가 `traces/sample/`에 정책 5종(P-WD, P-WW, B1, P-ALL, P-ORD)의 작은 트레이스(T = 4, R = 5)를 만든다. 형식 시험용이다.
- 검증기: `python3 -I traces/validate.py 파일.jsonl`. 형식 문서 §3의 여섯 검사.
- 변환기: `traces/convert.py`의 `trace_to_programs`가 트레이스를 락 프로그램으로 바꾼다(형식 문서 §2의 기준 구현).
- 자체 점검: `python3 -I traces/check_validate.py`가 `formal/rq3/trace-validator-check.md`를 만든다.

## 6. 만들지 않은 것: 시간 모델을 가진 시뮬레이터(모드 S)

`prereg/RQ3.md` §5의 M5(완료 시간), M6(대기 시간), M7(중단 횟수)의 일부는 시간을 가진 이산 사건 시뮬레이션이 필요하다. 이 시뮬레이터는 임계구역 길이(`work`)와 롤백 비용(ρ_rb), 백오프, 탐지 주기를 쓴다. 만들지 않은 이유는 두 가지다. (1) 백오프 분포, 재시도 상한 R_max, 타임스탬프 재사용(O3-5), 탐지 시점(O3-14), wound의 시점(O3-12)이 사람의 결정이거나 파일럿 뒤에 정해지는 값이다. (2) 정책의 순위를 보여 주는 수치를 내는 도구라서 사전등록이 동결되기 전에 돌려 보는 것은 규칙에 어긋난다(`prereg/README.md` §4). 위 결정이 정해지면 만든다. 이 문서의 생성기와 락 표는 그때 그대로 쓴다.

## 7. 점검 결과

두 가지 점검이 있고 둘 다 정책의 성능을 말하지 않는 도구 시험이다(2026-11-02 실행, 코어 2개).

**생성기·실행기 점검**(`bench/check_workloads.py` → `formal/rq3/workloads-check.md`, 검사 23개, 실패 0개, 약 0.5분).
- 생성기(A1–A7): 같은 시드는 같은 워크로드, 모든 작업이 올바른 락 프로그램, 순서 위반 비율이 p_v와 5 표준오차 이내로 같음, Zipf 선택 빈도가 이론 가중치와 같음, 락 번호 무작위화(O3-19), 임계구역 길이 분포의 평균, L2 구조.
- 연기 시험(B): 핵심 격자 27셀 × 정책 11개 × 인스턴스 6 × 스케줄 시드 2 = 3,564회 실행. 예방·회피 정책 9종은 불변식 위반과 교착 집합이 없고 모두 정상 종료했다. 탐지 정책 B1은 교착이 실제로 생겼다가 풀려 모두 종료했다. 무정책 B0는 깊이 1이거나 p_v=0인 셀(15개)에서 한 번도 멈추지 않았고(정리 T6와 일치) 깊이 2 이상이며 p_v>0인 셀(12개)에서는 144회 중 64회 멈췄다. 그래서 이 격자는 정책이 할 일을 실제로 만든다. P-RAG와 P-BNK의 무작위 실행은 같은 시드에서 완전히 같았다(324쌍).
- 경쟁 라벨의 타당성: Zipf 지수가 커질수록 정적 겹침(두 작업이 락을 공유할 확률)이 모든 깊이에서 늘고, 동적 충돌 비율(B0, 균등 무작위 스케줄)도 양 끝에서 늘었다. 깊이 4에서는 s=0.8 → 1.2의 동적 증가가 작다(0.337 → 0.350). **이 점검은 한 번 실패한 뒤 바꾼 것이다**: 첫 판은 동적 비율의 엄격한 단조 증가를 80회 표본으로 요구했고 깊이 4에서 0.343 대 0.340으로 실패했다. 생성기는 바꾸지 않고 점검을 정적 단조 + 동적 양 끝 비교로 바꾸고 표본을 늘렸다(사후 변경, 보고서에 기록). 실제 충돌 비율은 라벨(Zipf 지수)과 별개로 보고해야 한다는 `prereg/RQ3.md` §4.4의 요구가 그래서 필요하다.

**트레이스 검증기·변환기 점검**(`traces/check_validate.py` → `formal/rq3/trace-validator-check.md`, 검사 45개, 실패 0개, 약 2초). 정책 11개 × 작은 워크로드 12종 × 인스턴스 2 × 스케줄 시드 3 = 정책당 72회 실행을 트레이스로 기록해 검증기에 넣었다(양성). 일괄 요청이 아닌 정책은 트레이스를 락 프로그램으로 되돌려 원래 프로그램과 같은지 비교했다(왕복 불일치 0). 위반을 일부러 넣은 트레이스 30개(손으로 만든 것과 합성 견본을 고쳐 만든 것)를 검증기가 규칙별로 잡는지도 시험했다(음성). 변환기 단위 시험 3개가 더 있다. 합성 견본 5개는 오류·경고가 없다.

확인하지 않은 것: 시간 모델이 필요한 모든 것, 정책 사이의 비교, 스레드당 작업이 둘 이상인 실행, T와 R의 일차원 스윕. 아래 한계 절 참조.

| O3-25 | 스레드당 작업 수와 작업 사이의 간격 | 1(현재). 여러 작업을 이으려면 시간 모델과 간격 분포가 필요 | 동결 전 |
| O3-26 | 시간 모델 시뮬레이터(모드 S)의 사양 | §6의 결정이 정해진 뒤 별도 문서 | 동결 전 |

## 9. 한계

- 생성기와 점검을 같은 사람(AI)이 썼다. 통계 점검은 5 표준오차 대역이라 작은 편차를 놓칠 수 있다.
- L1은 합성이다. 실제 응용의 락 사용(분기, 조건 변수, 읽기·쓰기 모드, 재진입)을 닮았다고 말하지 않는다.
- 무작위 스케줄은 균등 선택이라 실제 스케줄러의 편향(코어에 붙는 스레드, 우선순위)을 담지 않는다. 이 스케줄에서 본 충돌 비율은 시간 모델 아래의 값과 다를 수 있다.
- 모든 락이 배타적이고 단일 인스턴스이며, 한 작업이 같은 락을 두 번 얻지 않는다.
