## 1. 기호와 입력

문서 04 §2.1의 기호를 쓴다. 문헌의 d는 m으로 옮겨 적고 원문 기호를 병기한다.

| 기호 | 뜻 |
|---|---|
| n | 프로세스 수 (프로세스 번호 0 … n−1, 훑는 순서 = 번호 순서) |
| m | 자원 종류 수 |
| Total[r] | 종류 r의 총 단위 수 (양의 정수) |
| Alloc[p][r] | 프로세스 p가 쥔 단위 수 |
| Max[p][r] | 프로세스 p가 선언한 최대 청구량 |
| Need[p] = Max[p] − Alloc[p] | 앞으로 더 청구할 수 있는 양 |
| Avail[r] = Total[r] − Σ_p Alloc[p][r] | 가용량 |

유효한 상태: 0 ≤ Alloc ≤ Max ≤ Total, 종류마다 Σ_p Alloc[p][r] ≤ Total[r]. 벡터 비교 a ≤ b는 모든 성분에서 a[r] ≤ b[r]이다. `oracle/banker.py`의 `Banker`가 이 조건을 검사한다.

## 2. 안전 상태의 정의와 오라클

**정의(교재식).** 상태 s가 **안전**하다 ⇔ 프로세스의 모든 순열 가운데 다음을 만족하는 안전 순서가 있다: 순서대로 프로세스 p를 하나씩 끝낼 때마다 Need[p] ≤ Work이고, 끝낸 뒤 Work += Alloc[p] (Work의 처음 값은 Avail). 안전하지 않으면 **불안전**이다. 불안전은 교착이 일어난다는 뜻이 아니라 '보장하지 못한다'는 뜻이다(F8의 서술에 대한 AI의 정리. 원문 재확인 전).

**정확 오라클 O1** (`oracle/banker.py`, 모델 명세 §3.5). 안전 ⇔ 요청을 {Need}로 둔 SM 상태 s_max에 교착 집합이 없다. 같은 모듈에 독립 구현이 둘 더 있다(순열 n!개 전수 `safe_perm`, 완료 집합 위의 DP `safe_dp`). 세 판정은 소규모 889,373개 상태에서 일치했다(`formal/rq6/o1-check-results.md`).

## 3. 교재식 안전성 알고리즘

**의사코드(교재식).** 교재의 설명을 AI가 옮긴 것이다(X).

```
safe(Avail, Alloc, Need):
  1. Work := Avail;  Finish[i] := false (모든 i)
  2. Finish[i] = false 이고 Need[i] ≤ Work 인 i를 찾는다. 없으면 4단계로
  3. Work := Work + Alloc[i];  Finish[i] := true;  2단계로
  4. 모든 i에서 Finish[i] = true 이면 안전, 아니면 불안전
```

2단계 "찾는다"를 어떻게 하느냐에 따라 비용이 다른 두 구현이 있다. **판정은 같다.** (이유: 프로세스 p가 끝낼 수 있는 조건 Need[p] ≤ Work에서 Work는 끝낸 프로세스가 늘수록 커지기만 하므로, 한 번 끝낼 수 있는 프로세스는 계속 끝낼 수 있다. 그래서 어떤 순서로 끝내든 더 끝낼 수 없을 때의 끝낸 집합은 같다. 이것은 오라클의 'greatest deadlock set' 계산과 같은 닫힘 연산이다. 일치는 §7의 전수 대조로도 확인했다.)

| 구현 | 2단계 | 코드 |
|---|---|---|
| **Restart** | 끝낼 때마다 i = 0부터 다시 훑어 처음 찾은 i를 끝낸다. 교재 의사코드를 글자 그대로 옮긴 형태 | `bench/policies/banker/textbook.py::TextbookRestart` |
| **Sweep** | i = 0 … n−1을 한 번 훑는 동안 찾는 대로 끝내고(끝낸 프로세스는 건너뛴다), 한 번 훑어 진전이 없을 때까지 되풀이 | `…::TextbookSweep` |

기준 구현의 기본값은 Restart로 제안한다(교재 의사코드에 가장 가깝기 때문이다). 두 구현을 모두 보고하며, 어느 쪽이 '기준'인가는 §9의 R-1이다. 문헌의 개선 주장이 두 구현 가운데 어느 쪽과 비교하는지에 따라 개선 폭이 달라질 수 있다.

## 4. 자원 요청 알고리즘

프로세스 i가 벡터 req를 요청한다. 교재식 절차(AI 옮김, X):

```
request(i, req):
  1. req ≤ Need[i] 가 아니면 ERROR   (최대 청구 초과)
  2. req ≤ Avail 이 아니면 WAIT      (가용량 부족. 안전성 판정 이전의 대기)
  3. 허가한 것으로 가정한다: Avail −= req;  Alloc[i] += req;  Need[i] −= req
  4. 가정한 상태가 안전이면 GRANT(그대로 둠), 아니면 DENY(가정을 되돌림)
```

`oracle/banker.py::request_outcome`이 같은 의미를 오라클로 옮긴 것이다. 구현(`SafetyPolicy.request`)은 호출이 끝나면 상태를 그대로 되돌린다(허가의 반영은 호출하는 쪽의 일). 영벡터 요청은 '아무것도 바꾸지 않는 요청'으로 보고 현재 상태의 안전성에 따라 GRANT 또는 DENY가 된다.

**성질(도출).** 허가한 뒤의 상태 s'가 안전하면 허가하기 전의 상태 s도 안전하다. s'의 안전 순서 π를 s에 그대로 쓴다. i가 아닌 프로세스 q가 끝나는 시점의 Work는 s에서 s'보다 같거나 크다(π에서 i가 q보다 앞이면 s'에서 Avail이 req만큼 줄고 Alloc[i]가 req만큼 늘어 같고, 아니면 s'가 req만큼 작다). q의 Need는 두 상태에서 같으므로 Need[q] ≤ Work가 s에서도 성립한다. i 자신이 끝나는 시점의 Work는 s가 s'보다 req만큼 크고 Need[i]도 req만큼 크므로 부등식이 그대로 성립한다. 따라서 **불안전 상태에서는 GRANT가 나오지 않는다.** 이 성질은 전수 점검의 속성으로도 확인했다(§7).

## 5. 비용 단위 (K2의 정의)

`bench/ops.py`가 아래를 센다. 정책 구현은 비교와 덧셈을 이 객체의 메서드로만 한다.

| 필드 | 뜻 | 비고 |
|---|---|---|
| `vec_cmp` | 벡터 비교(a ≤ b) 호출 횟수 | 문헌의 'n² 번의 비교'에 대응하는 후보 |
| 스칼라 비교(전체) = `vec_cmp` × m | 모든 성분을 비교한다고 본 스칼라 비교 횟수 | **기본 단위 제안.** 문서 04 §2.2의 제안(스칼라 비교 1회)을 구현 세부(단락 평가)에 덜 의존하게 정한 것 |
| `sca_cmp` | 실제로 수행한 스칼라 비교 횟수(첫 실패에서 멈춤) | 구현 세부에 의존. 보조로 보고 |
| `vec_add` | 벡터 덧셈·뺄셈 횟수 | 안전성 알고리즘에서는 끝낸 프로세스 수와 같다 |
| `iters` (+`sweeps`) | 안쪽 반복 방문 횟수 (+ Sweep의 훑기 횟수) | 끝난 프로세스를 건너뛰는 방문을 포함. 비교 횟수에 안 잡히는 비용이다(§6 끝, R-3) |

문헌의 비용 표기(Θ(mn²), O(n²d), O(n³d), O(n²×m))가 위 필드 가운데 무엇을 센 값인지는 본문을 읽기 전에는 모른다(문서 04 §2.3). 이 문서는 어느 표기도 오류라고 하지 않으며, 표기를 위 단위 가운데 하나로 옮길 수 있는지는 주장 단위 부록에서 주장마다 적는다.

## 6. 사례 범주와 최악 입력

기준 구현에서 한 번의 안전성 검사(`is_safe`)에 대해 다음을 정의한다. k는 끝낸 프로세스 수(= O1의 끝낼 수 없는 집합의 크기를 n에서 뺀 것)이다.

**벡터 비교 횟수의 범위: n ≤ vec_cmp ≤ n(n+1)/2** (Restart, Sweep 모두).

*하한 도출.* 끝낸 프로세스마다 성공한 비교가 한 번 있고(k번), 끝내지 못한 프로세스마다 마지막 훑기에서 실패한 비교가 한 번 이상 있다(n−k번). 합계 ≥ n.

*상한 도출.* Restart에서 t번째로 끝내기 직전의 미완료 프로세스는 n−t+1개이고 한 번 훑는 동안 각 미완료 프로세스는 최대 한 번 비교된다. 끝낸 뒤 마지막 훑기는 남은 n−k개를 모두 비교한다. 그러므로 vec_cmp ≤ Σ_{t=1}^{k}(n−t+1) + (n−k) = (k+1)(2n−k)/2 = f(k). f(k+1) − f(k) = n−k−1 ≥ 0 (k ≤ n−1)이므로 f는 k에 대해 줄어들지 않고 f(n) = n(n+1)/2이다. Sweep은 훑기마다 미완료 프로세스를 최대 한 번씩 비교하고, 진전이 있는 훑기는 최소 하나를 끝내므로 같은 합으로 막힌다.

*불안전 입력의 상한.* 불안전하면 끝낼 수 없는 프로세스가 둘 이상이다(하나만 남을 수 없다: 나머지가 모두 끝났다면 Work = Total − Alloc[p] ≥ Max[p] − Alloc[p] = Need[p]이므로 p도 끝낼 수 있다. Max ≤ Total이 쓰였다). 그래서 k ≤ n−2이고 f(n−2) = n(n+1)/2 − 1이 상한이다.

**최악 입력(F-bound).** `bench/gen_banker.py::worst_case(n, m, kind)`:

| kind | 구성 | 판정 | 벡터 비교(두 구현) |
|---|---|---|---|
| `chain-first` | 총량 n+1, 모든 프로세스 보유 1(가용 1), 프로세스 p의 필요량은 모든 종류에서 n−p. 끝낼 수 있는 프로세스가 매번 하나(맨 뒤 것)뿐 | 안전 | n(n+1)/2 |
| `chain-last` | 위와 같되 필요량이 마지막 종류에만(앞 종류는 0) | 안전 | n(n+1)/2, 스칼라(전체 = 실행) m·n(n+1)/2 |
| `chain-unsafe-first/last` | 앞의 두 프로세스를 서로 기다리는 쌍(필요량 n)으로 바꿈. 쌍이 맨 앞이라 훑을 때마다 실패 비교가 둘 더 든다 | 불안전 | n(n+1)/2 − 1 |

`chain-first`는 첫 성분에서 비교가 실패하므로 실행 스칼라 비교가 vec_cmp 쪽으로 줄어든다. `chain-last`는 단락 평가가 효과가 없는 입력이라 스칼라 비교가 m·vec_cmp에 이른다. 이 둘이 같은 벡터 비교 횟수에서 스칼라 비교 횟수를 다르게 만드므로 K2는 둘을 따로 보고한다. 소규모 점검에서 두 공식을 n = 2–33, m = 1–3에서 확인했다(`formal/rq6/harness-check-results.md`). Sweep의 훑기 횟수는 이 입력에서 n이다.

**평균 사례.** 평균은 입력 분포를 정해야 정의된다. 기준 구현에는 정해진 분포가 없다. 평균 주장은 저자가 적은 분포를 주장 단위 부록에 옮겨 그 분포(와 F-rand의 분포)에서 잰다. 분포를 쓰지 않은 '평균' 주장은 비교 불가 후보다.

**상각 사례.** 기준 구현은 한 번의 검사만 정의한다. 요청 열에 걸친 상각 주장(예: Belik 1987)은 요청 열과 상태 갱신 규칙을 주장 단위 부록에서 정한다.

**반복 방문 수와 시간의 차이.** Restart는 끝낼 때마다 처음부터 훑으므로 끝난 프로세스를 건너뛰는 방문이 생긴다. 이 방문은 벡터 비교 횟수에 안 잡힌다. 그래서 '쉬운' 안전 상태에서 Restart와 Sweep의 벡터 비교 횟수는 거의 같아도 시간이 달랐다(`bench/check_pipeline.py` 실행 중 표본 12개에서 시간 비 약 2, 비교 횟수 비 약 1.0. 표본이 작아 참고용이다). 문헌의 '비교 횟수' 척도가 이런 비용을 놓칠 수 있다는 뜻이다. K2에 `iters`를 보조 수량으로 넣을지는 R-3이다.

## 7. 판정 의미의 기준과 점검 결과

K1(판정 일치)의 정의: 입력 상태마다 구현의 판정을 O1과 대조한다. **FU**(거짓 불안전) = O1 안전, 구현 불안전(보수적). **FS**(거짓 안전) = O1 불안전, 구현 안전(비보수적). 요청 판정은 오라클 GRANT인데 구현 DENY가 보수적, 오라클 DENY인데 구현 GRANT가 비보수적이다.

점검 결과(`formal/rq6/policies-diff-results.md`, `bench/check_banker_policies.py`): 9개 소규모 범위의 모든 상태 889,373개에서 Restart, Sweep, numpy 닫힘의 안전성 판정이 O1과 모두 일치했다(FU = FS = 0). 속성 위반도 0건이다(벡터 비교 ≤ n(n+1)/2, 벡터 덧셈 = n − O1의 끝낼 수 없는 집합 크기, `is_safe`가 상태를 바꾸지 않음). 요청 판정은 범위 안 요청과 ERROR·WAIT 탐침 5,133,952건(두 구현의 합)과 전 요청 공간(영벡터 포함) 1,342,336건(두 구현의 합)에서 O1의 `request_outcome`과 모두 일치했고 (불일치 0), 호출 뒤 상태 복원 실패 0건, '불안전 상태에서 GRANT' 0건이었다. 같은 점검이 고의로 틀린 정책 5종을 모두 잡았다(n = 3, 총량 [2, 2]). 벡터 비교 횟수의 최댓값은 n = 3–4의 여러 범위에서 상한 n(n+1)/2와 같아 이 범위에서 상한이 달성된다(총량이 작은 범위는 상한에 못 미친다: n = 4, [1, 1]은 9, n = 5, [1, 1]은 13). 이 일치는 같은 정의를 다른 코드로 계산한 값끼리의 일치이며, 교재의 정의와 같다는 뜻이 아니다(R-4).

## 8. 큰 입력의 정답과 O1의 크기·시간 한계

동결 뒤 본 실행에서 입력마다의 정답은 O1(`safe_oracle`)로 구할 수 있는가? 측정한 범위에서는 가능하다. F-rand의 가장 큰 입력(n = 4096, m = 256)에서 O1이 143 ms, 최악 입력(chain-last, n = 4096, m = 8)에서 4.4초였고, 측정한 모든 크기에서 O1, numpy 닫힘, 두 교재식 구현의 판정이 같았다(`formal/rq6/policies-diff-results.md` §5, 입력 수는 크기마다 1–4개). 최악 입력에서 O1의 시간은 n²에 가깝게 늘었다(n = 256: 17 ms, 1024: 272 ms, 4096: 4.4초). 그러므로 크기 격자의 끝(n ≤ 4096, m ≤ 256)까지 입력마다 O1로 대조해도 입력당 최대 수 초이고, 부담이 되면 표본 대조로 줄일 수 있다(R-8). 주의: F-rand의 큰 입력은 닫힘 반복이 적은 '쉬운' 입력이었을 수 있어 어려운 입력에서의 시간은 더 걸릴 수 있다. 입력 난이도 분포는 파일럿에서 본다(`bench/README.md`). 같은 표에서 Restart는 큰 F-rand 입력(n = 4096, m = 64)에서 Sweep보다 17배쯤 느렸다(134.6 ms 대 7.8 ms). 벡터 비교 횟수로는 설명되지 않는 차이이며 §6 끝의 반복 방문 수 문제와 같은 종류다(표본 4개, 참고용).

## 10. 한계

- 상한·하한과 판정 동치는 이 문서 안의 도출이다. 코드와 소규모 전수, 최악 입력에서 맞춰 보았을 뿐 증명 검사기로 확인하지 않았다.
- 교재 의사코드는 원문과 대조하지 않았다(X). 문헌 변형이 '교재식'이라고 부르는 것이 여기의 구현과 같은지는 변형 논문을 읽을 때 확인한다.
- 소규모 일치는 큰 입력의 일치를 보장하지 않는다.
- 기호 d와 m의 대응, 비용 표기가 센 단위는 문헌마다 확인해야 한다.
