## 1. 범위, 원칙, 현황

### 1.1 원칙

1. 논문의 의사코드와 순서도를 글자 그대로 옮긴다. 논문이 정하지 않았거나 모호한 곳은 '해석 항목'으로 드러내고, 읽기가 둘 이상이면 이름이 다른 정책으로 구분한다. 어느 해석이 '대표'인지는 동결 뒤의 주장 부록에서 사람이 정한다(지금은 대표를 정하지 않는다).
2. 변형은 오라클 O1과 비교하지 않는다. 오라클과의 불일치가 K1이 재는 대상이기 때문이다(`prereg/RQ6.md` §5). 점검은 (가) 문헌 예제 재현, (나) 같은 해석의 두 번째 독립 구현과의 차등, (다) 속성, (라) 일부러 틀린 구현(변이체)의 검출, (마) PDF와 옮긴 값의 대조다.
3. 손으로 이끌어 낸 서술은 '도출(AI), 사람 검토 대기'로 표시하고 코드로 확인한 범위를 적는다(`formal/rq6/variants-derivations.md`). 도출은 증명이 아니다.
4. 비용은 두 단위로 센다. `paper_cmp`는 논문이 센 비교만이고 `sca_cmp`는 실행한 모든 스칼라 비교다. 어느 쪽을 K2의 단위로 쓸지는 열린 항목이다(§6 V-3).
5. 표 값은 논문의 인쇄본에서 옮기고, 인쇄 불일치는 고치지 않고 드러낸다(§2.6, §3.6, §5.1.6, §5.2.6).
6. 변형의 판정을 오라클이나 닫힘 계산(오라클의 정의)과 견주지 않는 규칙(위 2)을 지키려고, '이 해석의 판정은 표준 정의와 같다/다르다'는 서술은 코드로 확인한 것과 확인하지 않은 것을 나누어 적는다. 코드로는 (가) 인쇄된 예제를 재현하는지, (나) 변형끼리 또는 기준 구현(`textbook-*`)과 계측 계수가 같은지, (다) 안전 순서를 되짚어 보인 증명서가 있는지만 확인한다. 그 밖의 서술은 '도출(AI), 확인하지 않음'으로 적고 동결 뒤에 확인한다(예: §5.2.7의 D7).

## 2. DBDAA (R6-07)

### 2.1 자료와 읽은 범위

Zohora MF, Farhin F, Kaiser MS, "DBDAA: A real-time approach to Dynamic Banker's Deadlock Avoidance Algorithm with optimized time complexity"(PLOS ONE 19(9): e0310807, 2024, doi:10.1371/journal.pone.0310807, CC BY). 저널본 PDF(18쪽)를 전문 읽었다. Algorithm 1(53줄), 표 2–9, 본문의 순서와 비교 횟수를 `verify_dbdaa_pdf.py`가 기계로 대조했다(54개, 실패 0). 그림 2–7은 기계 대조에 들어 있지 않다.

논문의 주장(인벤토리 R6-07): 비교 횟수가 최선 10 대 85, 평균 36 대 100, 최악 70 대 125이고, 시간은 최선 O(n), 평균·최악 O(nd), 원래 뱅커는 O(n²d)다. 평가는 손으로 만든 10프로세스·5자원 데이터셋 3개의 비교 횟수뿐이고 실측 시간은 없다.

### 2.2 알고리즘 요약(의역)

- 전처리(4–11줄): 모든 프로세스는 시각 0에 도착한다고 본다. 최대 청구가 어느 자원의 총량이라도 넘는 프로세스는 Unsafe_Sequence로 보낸다. 나머지는 Max_Need(Need 성분의 최댓값)의 오름차순으로 SRQ에 둔다.
- 프로세스 하나의 검사(12–43줄): SRQ의 맨 앞 프로세스를 꺼낸다. 안 표시된 자원에서 Max_Need(Need의 최댓값)와 Min_A(Available의 최솟값)와 각각의 위치 L1, L2를 구한다. Max_Need ≤ Min_A이면 한 번의 비교로 통과한다(모든 안 표시된 자원이 통과한다). 아니면 L1과 L2에서 Need > Available인지 본다. 하나라도 그러면 그 프로세스는 Primary_Unsafe_Sequence로 가고, 아니면 두 자원을 표시하고 되풀이한다. ⌊d/2⌋번 뒤에 안 표시된 자원이 하나 남으면(d 홀수) 그 자원(L3)만 직접 확인한다. 통과하면 Safe_Sequence에 넣고 Available에 Allocation을 더한다.
- 주기(44–50줄): 타이머가 한 주기 m을 정한다. 타이머가 닿거나 SRQ가 비면 세 순서(Safe_Sequence, Primary_Unsafe_Sequence, Unsafe_Sequence)를 돌려주고, Primary_Unsafe의 프로세스는 SRQ로 되돌아가 다음 주기에 다시 검사한다.

### 2.7 도출(AI), 사람 검토 대기

`formal/rq6/variants-derivations.md`에 코드로 확인한 범위가 있다. 입력은 손으로 만든 것과 점검용 입력이며 등록된 입력군이 아니다. 숫자는 K1·K2·K3의 결과가 아니다.

- **D5**: 정렬 동률 규칙(Z-4)은 단일 훑기 판정을 바꾼다.
- **repeat 읽기의 판정**(코드로 확인하지 않음): 안 끝난 프로세스를 정렬 순서로 되풀이해서 훑고 진전이 없을 때 멈추면 끝난 집합은 순서와 무관한 닫힘(가장 큰 완료 가능 집합)이므로 이 읽기의 판정은 닫힘 계산(`reference.md` §2의 안전 정의)과 같을 것이다. 그렇다면 `dbdaa-repeat`의 K1은 구현 점검의 성격이고 흥미로운 지표는 K2·K3다. 이 서술은 동결 전에 오라클과 변형을 비교하지 않는 규칙(`prereg/RQ6.md` §5) 때문에 코드로 확인하지 않았다. 동결 뒤에 확인한다.

### 3.2 알고리즘 요약(의역)

- 자료: 프로세스별 최대 청구, 현재 할당, 자원 총량, 가용량, Need, 프로세스별 '최대 필요량'(Need 성분의 최댓값), 가용량의 최솟값(Minimum Available).
- 1–2단계: 완료 표시를 지운다. 어떤 프로세스의 최대 청구가 어느 자원의 총량이라도 넘으면 불안전을 돌려준다.
- 3단계: 프로세스를 최대 필요량의 오름차순으로 기수 정렬한다. 같은 키는 입력 순서를 유지한다(예제의 표 III).
- 4단계: 정렬된 순서로 한 번만 훑는다. 프로세스의 최대 필요량 ≤ 최소 가용량이면 자원을 일일이 보지 않고 끝낼 수 있다(비교 1회). 아니면 자원을 하나씩 확인한다. 끝낼 수 있으면 안전 순서에 넣고 Available에 할당량을 더하고 최소 가용량을 다시 구한다. 끝낼 수 없으면 불안전을 돌려준다(순서도).
- 5–6단계: 끝나지 않은 프로세스가 있으면 불안전, 없으면 안전과 안전 순서를 돌려준다.
- 본문은 순서를 한 번 이상 확인할 필요가 없다고 쓴다.

### 3.3 구현

`bench/policies/banker/variants/begum2020.py`의 `BegumReturn`(정책 `begum-return`)이 위 단계를 옮긴다. 기수 정렬은 표준 LSD 계수 정렬(10진)로 직접 옮겼다(`radix_order`). 계수는 DBDAA와 같은 방식이다: `paper_cmp`(빠른 검사 + 자원별 검사. 논문이 센 '10회'는 빠른 검사만이다), `quick_cmp`, `res_cmp`, `admit_cmp`(2단계), `maxneed_cmp`(최대 필요량 계산), `min_cmp`(최소 가용량 계산), `sca_cmp`(전체), `radix_passes`(기수 정렬의 자리 수. 비교 연산이 아니라 `sca_cmp`에 넣지 않았다), `vec_add`, `iters`.

### 3.6 논문 안의 불일치와 모호

- 표 III의 P7 행에서 Needed allocation의 E칸이 5로 인쇄됐다(표 II와 Maximum − Allocation은 0). 표 IV의 P7 행에서는 Maximum Needed allocation이 5로 인쇄됐다(표 II·III은 7). 둘 다 PDF에도 그대로 있다. 실행 결과에는 영향이 없다(P7의 비교는 7과 5 어느 쪽이든 최소 가용량 18 이하라 True).
- 의사코드는 빠른 검사를 '≤'로 쓰고 본문의 설명 문장은 '미만'이라고 쓴다. 예제의 표 IV는 P4에서 2 ≤ 2를 True로 적으므로 '≤'가 맞다.
- 순서도의 반복 변수 i는 0에서 시작하고 판정은 i ≤ n이다(n + 1번 돈다). 의사코드는 1 ≤ i ≤ n이다. 표기 문제이며 영향이 없다고 보았다.
- 'j == d' 판정(B-2)과 기수 정렬의 자릿수 추출식(B-4)은 문자 그대로는 맞지 않는다.
- 3단계(정렬)를 O(nd)라고 쓴다. 이 구현에서 정렬 자체는 O(n·자리 수)이고 최대 필요량 계산이 O(nd)다. 복잡도 합계 O(n + nd + nd + nd) = O(nd)와 '원래 뱅커보다 n배 빠르다'는 결론은 원래 뱅커의 안전성 검사를 O(n²d)로 보는 것에서 나온다. 이 주장들은 동결 뒤에 K4(기울기)로 다룰 수 있는지 정한다(V-3).

## 4. 두 변형을 함께 보면

1. **판정이 같다(도출 D3, 코드 확인).** `begum-return`과 `dbdaa-cycle1`은 같은 키로 정렬해 각 프로세스를 그 시점의 Available에 대해 '모든 자원에서 Need ≤ Available'인지 보고, 안전은 '정렬 순서 전체가 안전 순서'다. 두 정책의 안전 판정은 46,691개 입력에서 같았고 begum의 안전 순서는 dbdaa-cycle1이 통과시킨 순서의 접두사였다. 두 알고리즘은 실패한 프로세스를 다루는 방식(begum은 멈추고 DBDAA는 건너뛰어 계속하고 다음 주기에 되돌린다)과 비용에서만 다르다.
2. **함의(도출).** 이 읽기들에서는 판정 함수가 같으므로 판정 정확도(K1)를 따로 재면 같은 값이 나온다. 비교 횟수와 시간(K2, K3)은 다르다. 인벤토리의 재구현 가능 건수(N_min 판단, Q8)를 셀 때 두 항목은 판정에 관해서는 독립 증거가 아니고 비용 주장에 관해서만 독립이다. 결정은 사람 몫이다.
3. **DBDAA의 되풀이 읽기**(`dbdaa-repeat`)는 두 단일 훑기 읽기와 판정이 다르다(Z-2). 어떤 읽기가 논문의 뜻인지가 열린 항목이다.
4. **Begum 구현에 대한 별개의 문헌 증거.** DBDAA 저자들이 Begum 알고리즘을 자기 입력에 돌려 얻었다고 적은 값(10회, 불안전, 불안전)을 이 저장소의 `begum-return`이 재현한다. 이 값은 Begum 논문과 별개의 문헌에서 온 것이다(DBDAA 저자들이 같은 읽기를 썼다는 보장은 없다).
5. **Wicaksono는 도착이 없으면 교재식 Sweep과 같은 경로다(코드 확인).** 도착이 없을 때 `wicaksono-sweep`은 `textbook-sweep`과 계측 계수(vec_cmp, sca_cmp, vec_add, iters, sweeps)가 같다(27,956개 입력에서 다른 경우 0. 판정을 직접 견준 것은 아니며 같은 계수는 같은 경로를 시사한다). 다른 점은 도착 인터페이스(바깥 반복의 맨 앞에서 한 번 확인)와 도착 때의 Need 재계산 비용(`need_ops`)이다. 도착이 받아들여지기만 하면 도착 시점은 안전 순서와 비교 횟수만 바꾸고 error 여부는 바꾸지 않았다(도출 D6, 코드 확인, 증명 아님). 그래서 R6-06을 재구현 가능 건수(Q8)에 셀 때 판정에 관해서는 `textbook-sweep`과 구별되는 증거가 아니고, 논문에 정량 주장이 없어 비용에 관해서도 대조할 주장이 없다. 결정은 사람 몫이다.
6. **Dixit·Khuteta는 한 알고리즘이 아니라 여섯 개의 보완이다.** 논문의 의사코드는 스택 처리, Available에 되돌리는 양, 정렬 키를 정하지 않는다. 이 저장소는 되돌리는 양(release: max, alloc) × 스택 처리(tail: once, top, repeat)의 여섯 정책을 두었고, 예제의 인쇄된 추적과 스택 순서는 여섯 모두 재현한다. 판정은 정책마다 다를 수 있다. 프로세스 번호를 바꾸면 판정이 달라지는 상태의 수가 정책마다 다르고(`max-repeat`만 0), `top`은 교재식 안전 순서가 있는 상태를 불안전이라 할 수 있다(§5.2.7의 D8, D9). 예제만으로는 어느 보완이 저자의 뜻인지 정해지지 않는다. 스택의 프로세스가 '위에서부터 실행된다'는 서술을 만족시키는 것은 `release = max`의 `top`과 `repeat`뿐이다(§5.2.5).
7. **네 변형의 구조(서술).** 한 번 훑고 마는 구조(`begum-return`, `dbdaa-cycle1`, `dixit-*-once`)와 진전이 없을 때까지 되풀이하는 구조(`dbdaa-repeat`, `wicaksono-sweep`, `dixit-*-repeat`)가 있고, 정렬 키가 있는 변형(DBDAA, Begum, Dixit)과 없는 변형(Wicaksono)이 있다. 이는 구현 구조의 분류이며 판정이 같다는 뜻이 아니다. 코드로 확인한 판정 동치는 위 1의 한 쌍(`begum-return`, `dbdaa-cycle1`)뿐이다. 되풀이하는 읽기가 닫힘 계산과 같을 것이라는 서술(`dbdaa-repeat`는 §2.7, `dixit-max-repeat`는 §5.2.7의 D7)은 동결 뒤에 확인한다.

## 5. Wicaksono 외 2023(R6-06)과 Dixit·Khuteta 2017(R6-04)

두 논문 모두 PDF를 기계로 대조하지 못했다. 숫자는 열람 도구가 읽어 요약한 텍스트에서 옮겼고 값 사이의 중복(Need = Max − Allocation, 자원 총량 등)으로 정합성만 점검했다. 인쇄본과의 일치는 보장하지 않으며 사람이 PDF를 눈으로 대조하면 풀린다(§6 V-14). 저작권 조건은 둘 다 확인하지 못해 문장은 옮기지 않았고 작은 예제의 최소 수치만 `bench/literature/`에 두었다.

### 5.1 Wicaksono 외 2023 (R6-06)

#### 5.1.1 자료와 읽은 범위

Wicaksono, Baeti, Salma, Kardian, "Banker's Algorithm Optimization to Dynamically Avoid Deadlock in Operating System", JEEMECS 6(1), 2023(인벤토리 R6-06, 문서 01의 M41. PDF 주소는 M41에 있다). 저널 사이트의 PDF를 열람 도구가 읽고 구조화해 돌려준 텍스트(2026-11-01, 인벤토리 W13)로 읽었다. 의사코드 그림 2–4와 표 1–5의 값을 옮겼다. 쪽 이미지는 보지 않았다.

논문의 주장: 실행 중에 새 프로세스가 도착하면 바깥 반복의 맨 앞에서 받아 Need를 다시 계산하고 같은 실행에 넣는 '동적' 최적화다. 예제의 서술은 표준 방식이면 새 요청이 한 번의 실행이 끝나는 시점(T4)까지 기다려야 하지만 제안 방식은 실행 중(T2)에 받아 안전 순서에 넣는다는 대비다. 결론은 교착이 없음을 '보장'한다고 쓰고 '실험적 검증'을 언급하나, 평가는 손으로 푼 예제 하나(자원 3종, 처음 프로세스 4개에 1개 도착)뿐이다. 복잡도 분석, 성능 측정, 원래 알고리즘과의 비교 실험, 정확성 논증이 없다. 코드는 의사코드이고 논문이 썼다는 파이썬 구현은 인쇄되지 않았다.

#### 5.1.2 알고리즘 요약(의역)

- `countNeed`(그림 2): 모든 칸에서 Need[i][j] = Max[i][j] − Allocation[i][j]를 다시 계산한다.
- `bankerLoop`(그림 3): Finish를 모두 거짓으로 두고, Finish에 거짓이 남아 있는 동안 바깥 반복을 한다. 바깥 반복의 맨 앞에서 새 요청이 도착했으면 Allocation에 0 행을, Max에 새 프로세스의 최대 청구 행을 붙이고 Need를 전부 다시 계산하고 프로세스 수와 Finish를 하나씩 늘린다. 이어 i = 0..M−1을 한 번 훑으며 Finish[i]가 거짓이고 Need[i] ≤ Available이면 i를 안전 순서에 넣고 Available에 Allocation[i]를 더하고 Finish[i]를 참으로 한다(훑는 도중 바뀐 Available을 뒤의 i가 본다). 한 프로세스도 끝내지 못했으면 'error'를 돌려준다.
- `main`(그림 4): Need를 계산하고 `bankerLoop`를 부른다. 결과가 'error'이면 안전 순서를 만들 수 없다고 쓴다.

도착이 없으면 이 구조는 교재식 Sweep(`textbook-sweep`)과 같다. 새로운 것은 도착을 받는 한 단계뿐이다.

#### 5.1.3 구현

`bench/policies/banker/variants/wicaksono2023.py`의 `WicaksonoSweep`(정책 `wicaksono-sweep`)이 위를 옮긴다. `run(st, ops, arrivals)`의 `arrivals`는 {바깥 반복 번호: 새 프로세스의 최대 청구 행}이다. `is_safe(st, ops)`는 도착 없이 돌려 'error가 아님'을 판정으로 쓴다. 호출자의 상태는 바꾸지 않는다(W-5).

| 계수 | 뜻 |
|---|---|
| `vec_cmp`, `sca_cmp` | 끝나지 않은 프로세스마다 하는 Need ≤ Available 비교(단락 평가) |
| `vec_add` | 끝낸 프로세스 수(Available += Allocation) |
| `iters`, `sweeps` | 훑기에서 본 칸 수(끝난 프로세스의 칸 포함), 바깥 반복 수 |
| `need_ops` | 도착 때마다 Need 전체를 다시 계산하는 스칼라 뺄셈: (그때의 프로세스 수) × (자원 종류 수) |

처음의 Need 계산(그림 4)은 입력 상태가 Need를 주므로 세지 않는다.

#### 5.1.6 논문 안의 불일치와 모호

- Available를 'M개 원소'라 쓴다(W-6). 새 프로세스의 (4, 3, 3)을 '요청'이라 부르면서 최대 청구로 쓴다(W-8). 시각 표지 T0–T5가 설명 없이 쓰이고 도착(T2)과 의사코드의 확인 위치를 잇는 서술이 없다(W-1, W-9).
- 새 프로세스를 받을 때 안전 여부를 확인하지 않고 'error'일 때 되돌리지도 않는다(W-4). 의사코드가 인자를 제자리에서 바꾼다(W-5).

- 열람 도구의 요약은 표 1의 Available 열이 p0 행에만 인쇄됐고 표 4가 끝난 p1·p3를 말없이 뺐으며 표 2와 표 5의 열 머리 순서가 다르다고 적었다. 도구의 서술이며 PDF를 눈으로 확인하지 않았다.

#### 5.1.7 도출(AI), 사람 검토 대기

- **D6 도착 확인 창**: 의사코드는 도착을 바깥 반복의 맨 앞에서 한 번만 확인하므로 (가) 모든 프로세스가 끝나 루프가 끝난 뒤에 도착한 프로세스와 (나) error로 끝난 뒤에 도착한 프로세스는 받아들여지지 않고 호출자에게 알려지지도 않는다. (가) 예제에 k = 3으로 도착을 요청하면 p1, p3, p0, p2가 끝나고 error가 아니며 도착은 받아들여지지 않는다. (나) Available이 (0, 0, 0)이고 모든 프로세스가 더 필요해 첫 반복에서 막히는 점검용 상태에서 k = 2로 요청하면 안전 순서가 비어 있고 error이며 도착은 받아들여지지 않는다. 같은 도착이 받아들여지기만 하면 도착 시점은 안전 순서와 비교 횟수만 바꾸고 error 여부는 바꾸지 않았다(점검 쌍 11,026개, 위반 0). 첫 반복의 도착은 처음부터 있던 프로세스와 같다(안전 순서, error, 반복 수, 계수가 같음. 점검 쌍 15,439개, 위반 0). 도출이며 증명이 아니다. 변형의 판정을 오라클이나 닫힘 계산과 견주지 않았다.

### 5.2 Dixit·Khuteta 2017 (R6-04)

#### 5.2.1 자료와 읽은 범위

Dixit, Khuteta, "A Dynamic and Improved Implementation of Banker's Algorithm", IJRITCC 5(8): 45–49, 2017(인벤토리 R6-04, M39). SlideShare에 올라온 제3자 사본(인벤토리 W03)의 본문을 열람 도구가 읽고 요약한 텍스트(2026-11-01, 인벤토리 W14. 앞서 B-4에서도 같은 쪽을 읽었다)로 읽었다. 저널 PDF가 아니고 도구의 요약이므로 인쇄본과 같다고 단정하지 않는다.

논문의 주장: 자원 개수를 실행 중에 바꿀 수 있는 '동적' 뱅커를 제안하고, 프로세스를 필요량 순으로 두어 풀이 시간을 줄인다고 서술한다. 정량 주장은 그림 2(프로세스 수 3, 6, 9, 12 대 실행 시간. y축 눈금 0–1400, 단위·자원 수·하드웨어·반복 수 없음)에서 나오는 '평균 약 9% 개선'뿐이고 계산 방법이 없다. 복잡도 분석은 없다(본문의 '이차 시간'은 선행 문헌 Lang 1999의 것이다). 결론은 결과가 이를 입증했다고 쓰나 시험은 그림 2뿐이다.

#### 5.2.2 알고리즘 요약(의역)

- 입력 서술: 필요량이 가장 작은 것이 위에 오는 스택. 출력: 안전 순서.
- 의사코드(네 줄): i = 0..n−1을 한 번 훑는다. Need(i) ≤ Available이면 Available에서 Need(i)를 빼고 프로세스를 실행하고 Available에 Allocation(첨자 없이 적힘)을 더하고 실행했다고 쓴 뒤 다음으로 간다. 아니면 필요량을 스택에 넣는다. 끝.
- 예제 설명: 넣을 때마다 '스택을 정리'해 필요량이 가장 작은 것이 위에 오게 하고, 스택에 남은 프로세스는 '위에서부터 실행된다'고 쓴다. 스택에서 꺼낸 프로세스를 다시 검사하는 단계, 종료 조건, 최종 안전 순서의 출력이 의사코드에 없다.

| ID | 항목 | 논문이 말하는 것 | 이 구현의 선택 | 근거 | 영향 |
|---|---|---|---|---|---|
| DK-1 | Available에 되돌리는 양(release) | 'Available = Available + Allocation'이 첨자 없이 적혀 있고 그 앞에서 Need(i)를 뺀다 | 정책 둘. `max`: 받은 뒤의 보유량(= Max)을 되돌린다(순효과 Available += Allocation_i, 교재식과 같음). `alloc`: 처음 보유량 Allocation_i만 되돌린다(인쇄된 식 그대로) | 인쇄된 식을 글자 그대로 읽으면 실행할 때마다 Available이 Need_i만큼 줄어 돌아오지 않는다. 예제의 P3 실행 뒤 Available은 `max`에서 (2, 3, 4), `alloc`에서 (2, 1, 1)이다 | 판정이 갈린다. `alloc`에서는 P3 뒤 스택의 어느 프로세스도 실행되지 못해, 스택의 프로세스가 실행된다는 서술과 맞지 않는다(§5.2.5) |
| DK-2 | 훑기 뒤 스택의 처리(tail) | 예제 설명이 '위에서부터 실행된다'고 쓴다. 다시 검사, 종료 조건, 최종 순서가 없다 | 정책 셋. `once`: 처리하지 않는다(훑기에서 모두 끝내지 못하면 불안전. 의사코드 그대로). `top`: 위에서부터 Need ≤ Available이면 꺼내 실행하고 위의 것이 실행되지 못하면 멈춘다(불안전). `repeat`: 스택을 위에서부터 훑어 되는 것을 실행하고 진전이 없을 때까지 되풀이 | 의사코드(`once`)와 예제 설명(스택 실행)이 어긋난다 | `top`은 교재식 안전 순서가 있는 상태를 불안전이라 할 수 있다(도출 D9) |
| DK-3 | 스택에 담는 것 | 의사코드는 '필요량'을 넣는다고 쓰나 예제 추적은 프로세스를 넣는다 | 프로세스 번호를 넣고 키는 그 프로세스의 Need에서 계산한다 | 예제의 스택 표기(P2, P4, P1, P0) | 없음(실행하려면 프로세스가 필요하다) |
| DK-4 | 정렬 키 | '필요량이 가장 작은 것이 위', '오름차순'. 벡터의 크기를 비교하는 규칙이 없다 | Need 성분의 합(작은 것이 위) | 예제의 인쇄된 스택 순서를 내는 키는 여럿이다(아래 표) | 키에 따라 판정이 달라진다. 점검 입력 23,148개에서 `max-top`의 판정이 Need 합 대신 제곱합이면 34개, Max 합이면 203개에서 달라졌다(도출 D10) |
| DK-5 | 같은 키의 순서 | 규칙이 없다. 예제에는 같은 키가 없다 | 먼저 넣은 것이 위(안정) | 예제 | `top`의 판정이 바뀔 수 있다(점검의 변이체 tie-lifo가 차등에 잡힌다) |
| DK-6 | 비교 연산 | 본문이 'less than'과 '≤'를 섞어 쓴다. 예제의 P3은 Need = Available에서 실행된다 | Need ≤ Available(같아도 통과) | 예제 추적의 P3 | '<'이면 첫 단계의 P3이 실행되지 않아 인쇄된 추적이 재현되지 않는다(변이체 strict-fit) |
| DK-7 | 스택 정리의 비용 | 정리 방법과 비교 횟수에 대한 서술이 없다 | 넣을 때마다 위에서부터 내려가며 자기보다 큰 키를 만날 때까지 비교하는 삽입으로 센다(`sort_cmp`). 키 계산(`key_add`)도 센다 | 논문에 정리 비용 서술이 없다 | 정렬을 다른 방식으로 읽으면 `sort_cmp`와 `key_add`가 달라진다. 이 비용을 K2의 단위에 넣을지는 V-3 |
| DK-8 | 구현하지 않은 것 | 추상이 실행 중 자원 수를 바꿀 수 있다고 쓰나 의사코드, 표, 예제에 규칙이 없다(본문은 자원 수가 줄 수 없다고도 쓴다고 도구가 적었다). 그림 2의 약 9%는 곡선 값과 실행 조건이 없다 | 구현하지 않았다. 9%는 재현하지 못한다 | — | 자원 수 변경은 이 저장소의 기준 모델(자원 총량 고정)과 다르다. 정량 주장의 범주는 V-13 |

예제의 인쇄된 스택 순서(위에서 P2, P4, P1, P0)를 내는 키 후보(DK-4. 같은 키는 번호 순)다.

#### 5.2.6 논문 안의 불일치와 모호

- 갱신식의 Allocation에 첨자가 없고 글자 그대로 읽으면 Available이 실행할 때마다 Need만큼 줄어든다(DK-1). 스택에 '필요량'을 넣는다고 쓰나 예제는 프로세스를 넣는다(DK-3).
- 스택 순서를 '필요량이 가장 작은 것이 위'와 '오름차순'으로 서술하나 넣고 꺼내는 규칙과 벡터의 비교 규칙이 없다(DK-2, DK-4). 훑기 뒤 스택을 처리하는 단계, 종료 조건, 최종 안전 순서의 출력이 없다(DK-2).
- 비교를 'less than'과 '≤'로 섞어 쓴다(DK-6). 추상은 실행 중 자원 수를 바꿀 수 있다고 하나 본문에 규칙이 없다(DK-8).
- 결론이 결과가 가설을 입증했다고 쓰나 시험은 조건 없는 그림 2뿐이다.

#### 5.2.7 도출(AI), 사람 검토 대기

- **D7 (`dixit-max-repeat`의 판정, 코드로 확인하지 않음)**: `release = max`이고 `tail = repeat`인 읽기는 안 끝난 프로세스를 되풀이해 훑고 진전이 없을 때 멈추므로 끝낸 집합이 닫힘(순서와 무관한 가장 큰 완료 가능 집합)이고, 따라서 판정이 교재식 닫힘 계산(`reference.md` §2)과 같을 것이다. 정렬된 스택은 비용과 안전 순서만 바꾸고 판정은 바꾸지 않을 것이다. 도출이며 증명하지 않았고, 동결 전에 변형의 판정을 오라클·닫힘 계산과 견주지 않는 규칙 때문에 코드로도 확인하지 않았다(동결 뒤에 확인한다). 이 점검이 본 간접 증거는 D8에서 번호 순열에 대해 `max-repeat`의 판정이 변하지 않았다는 것뿐이다.
- **D8 (실행 순서 의존)**: 프로세스 번호를 모든 순열로 바꿔 판정이 달라지는 상태의 수(소규모 전수의 일부 14,912개 중): `max-once` 9,737, `max-top` 790, `max-repeat` 0, `alloc-once` 3,103, `alloc-top` 672, `alloc-repeat` 374. `max-repeat`만 0이다(D7의 서술과 맞는다). 훑기를 번호 순으로 한 번만 하는 읽기(`once`)와 스택 위만 보는 읽기(`top`)는 번호에 의존하고, `release = alloc`의 `repeat`도 의존한다(Available이 줄어들 수 있어 실행 순서에 따라 갈린다). `alloc-repeat`의 예: 총량 (2, 2), Allocation [[0, 0], [0, 1], [0, 0]], Need [[0, 0], [0, 1], [0, 1]], Available (2, 1). 번호 순열 3개에서는 안전, 3개에서는 불안전이다. 이 상태에는 교재식 안전 순서 [0, 1, 2]가 있다(되짚기로 확인한 증명서).
- **D9 (`top`의 거짓 불안전)**: 위에서 실행하지 못하는 프로세스가 스택의 맨 위에 있으면 `top`은 멈추고 불안전을 돌려주지만, 그 아래 프로세스는 실행될 수 있다(벡터 필요량은 전순서가 아니라 '가장 작은 필요량'이 실행 가능한 프로세스를 가리지 못한다). 키가 모두 다른 최소 예: n = 3, 총량 (2, 1), Allocation [[0, 0], [0, 1], [1, 0]], Need [[0, 1], [2, 0], [0, 0]], Available (1, 0). 훑기에서 P2(번호 2)가 실행되고 스택은 위에서 P0, P1이다. `top`은 P0(Need (0, 1))이 실행되지 못해 불안전을 돌려주지만 `repeat`는 P1, P0도 끝내고, 그 실행 순서 [2, 1, 0]이 교재식 안전 순서임을 되짚기로 확인했다. 키가 같은 프로세스가 있는 최소 예(n = 3, 총량 (1, 1), Allocation [[0, 0], [0, 1], [1, 0]], Need [[0, 1], [1, 0], [0, 0]], Available (0, 0))도 같다. Begum 외의 D1(`variants-derivations.md`)과 같은 종류의 도출이다.
- **D10 (키 후보가 판정을 가른다)**: §5.2.4의 표에서 인쇄된 순서를 내는 키 셋 사이에서 `max-top`의 판정이 점검 입력 23,148개 가운데 Need 합 대신 제곱합이면 34개, Max 합이면 203개에서 달라졌다. 변형 사이의 비교이며 오라클과의 비교가 아니다.

| V-5 | 정렬 동률 규칙(Z-4, B-4)과 입력군에서 동률이 나오는 빈도 | 파일럿에서 동률 빈도를 확인한 뒤 규칙을 정한다. **파일럿 결과**(`docs/rq6/pilot.md` §7.4, F-rand 인스턴스 1,926개): 최대 Need 키(DBDAA·Begum)는 모든 인스턴스에서 겹치고, Need 합 키(Dixit)는 99.8%에서 겹친다(겹치지 않은 4개는 모두 n = 16). 동률은 예외가 아니라 거의 모든 입력에 있으므로 규칙은 정책 정의의 일부이며 동결 전에 정해야 한다 |

Dixit의 Allocation 키 세 변형은 같은 점의 F-rand 안전 입력에서 약 275 ms로 사슬 입력(3–5 ms)보다 오래 걸렸다. 정책마다 느린 입력이 다르다는 운영 관찰이며 정책 사이의 우열이나 변형별 최악 입력의 탐색이 아니다 |

## 7. 한계

- 구현은 논문의 서술을 옮긴 해석이다. 해석이 저자의 뜻과 같다는 보장은 없다. 두 번째 독립 구현은 같은 사람이 같은 이해로 쓴 것이라 옮기다 생긴 실수는 잡아도 해석의 오류는 잡지 못한다.
- 두 논문 모두 예제가 소규모(10×5)이고 일부 가지(Begum의 자원별 검사, DBDAA의 Z-4)는 예제가 쓰지 않는다. 그 가지는 차등과 속성으로만 점검했다.
- 도출은 증명이 아니다. 코드 확인은 점검 입력과 손으로 만든 입력에서 서술이 코드와 맞음을 보인 것이다.
- 오라클 O1과의 비교와 등록된 입력군 위의 비용·시간은 동결 전에 하지 않았다. 이 문서의 숫자는 K1·K2·K3의 결과가 아니다.
- PDF의 그림은 기계 대조하지 않았다. Begum의 서지(학회명, DOI)는 PDF에 없어 제3자 참고문헌(R6-14의 18번, S13)에 기댄다.
- Wicaksono와 Dixit·Khuteta의 값은 열람 도구가 읽은 텍스트에서 옮겼고 PDF와 기계로 대조하지 않았다(Dixit는 제3자 사본). 값 사이의 중복으로 정합성만 점검했으며 인쇄본과의 일치는 확인되지 않았다.
- Wicaksono의 도착 읽기(W-1)는 예제의 인쇄된 순서에 맞춘 것이다. Dixit의 여섯 정책은 서로 다른 보완이며 어느 것도 저자의 구현이라 할 수 없다. 이 저장소가 한 선택(Need 합 키, 삽입 정리, 안정 규칙)은 예제가 구별하지 못하는 선택이다.
- Wicaksono(처음 4개에 1개 도착, 자원 3종)와 Dixit(5개, 자원 3종)의 예제는 DBDAA·Begum의 예제(10개, 자원 5종)보다 작다. 이 두 변형의 가지는 대부분 차등과 속성으로만 점검했다.
- Dixit의 `max-repeat`가 닫힘 계산과 같을 것이라는 서술(D7)은 코드로 확인하지 않았다. 이 문서의 어느 서술도 변형의 판정이 오라클과 같다/다르다고 말하지 않는다.
