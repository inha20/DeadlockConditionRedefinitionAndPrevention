# traces/FORMAT — 락 트레이스 형식 (SI-3, AI 초안 v0.1)

- 작성일: 2026-11-01 (KST) · 작성: Claude(AI 조수) · **사람의 검토 전 · 동결 아님**
- 근거: 문서 02 §SI-3(이벤트 단위 레코드: 시각, 실행 문맥, 연산, 락·자원 식별자와 클래스, 모드, 호출 위치), `docs/rq3/policies.md` §1(락 프로그램 모델)
- 이 문서가 하는 일: RQ3가 정책을 재생하는 입력(L3 사용자 공간 트레이스, L4 커널 트레이스)과 합성 트레이스가 따를 파일 형식을 정한다. 형식 검증기는 `traces/validate.py`다.
- 하지 않는 일: 실제 응용의 트레이스를 수집하지 않았다(대상 응용 선정 O3-2와 Linux 환경 O3-3이 사람의 결정에 달려 있다). 제3자 원자료는 저장소에 두지 않는다(링크와 해시만).

## 1. 파일

JSON Lines(UTF-8, 한 줄에 JSON 객체 하나). **첫 줄은 머리 레코드**, 나머지는 이벤트 레코드이며 `seq` 순서로 정렬되어 있다.

### 1.1 머리 레코드

| 필드 | 형 | 뜻 |
|---|---|---|
| `trace_format` | 문자열 | `"rq3-trace-v0.1"` |
| `source` | 문자열 | `synthetic`(합성 생성기), `userspace`(pthread 가로채기 등), `kernel`(perf lock 등) |
| `generator` | 문자열 | 생성 방법과 버전(합성이면 생성기·정책·시드, 수집이면 도구와 버전·커널 버전·구성 옵션) |
| `clock` | 문자열 | `logical`(사건 순서 번호) 또는 `ns`(단조 시계 나노초) |
| `threads` | 정수 | 스레드 수 |
| `notes` | 문자열 | 자유 서술(선택) |

### 1.2 이벤트 레코드

| 필드 | 형 | 필수 | 뜻 |
|---|---|---|---|
| `seq` | 정수 | 예 | 전체 순서 번호. 0부터 1씩 증가 |
| `ts` | 수 | 예 | 시각. `seq` 순서에서 줄지 않는다 |
| `th` | 정수 | 예 | 실행 문맥(스레드) 번호 0..threads−1 |
| `task` | 문자열 | 예 | 작업 식별자. 작업 경계(`BEGIN`..`END`)를 구분한다 |
| `attempt` | 정수 | 예 | 같은 작업의 시도 번호(중단 뒤 재시작마다 +1) |
| `op` | 문자열 | 예 | 아래 연산 중 하나 |
| `lock` | 정수 | 락 연산에서 | 락 **인스턴스** 식별자 |
| `cls` | 정수 | 락 연산에서 | 락 **클래스** 식별자(락 순서 그래프의 노드; 합성에서는 `lock`과 같다) |
| `mode` | 문자열 | 락 연산에서 | `"X"`(독점). 공유 `"S"`는 형식에는 있으나 RQ3 정책은 아직 다루지 않는다 |
| `locks` | 정수 목록 | `WAIT`에서 선택 | 일괄 요청처럼 여러 락을 한꺼번에 기다릴 때 |
| `why` | 문자열 | `ABORT`, `FAIL`에서 선택 | 중단 사유(`deny`, `wound`, `detect`, `fail`) |
| `site` | 문자열 | 선택 | 호출 위치(파일:줄 등) |
| `ctx` | 문자열 | 선택 | 실행 문맥 종류(`task`, `irq`, `softirq` 등; 기본 `task`) |

### 1.3 연산

| `op` | 뜻 | 스레드 상태 변화 |
|---|---|---|
| `BEGIN` | 작업(의 한 시도) 시작 | 시작 → 실행 |
| `REQUEST` | 락 요청 | 실행 → (`ACQUIRE` 또는 `WAIT` 또는 `ABORT`/`FAIL`) |
| `WAIT` | 요청이 허가되지 않아 기다림 | 실행 → 대기 |
| `ACQUIRE` | 락을 얻음(요청 직후 또는 대기 끝) | 대기 또는 실행 → 실행 |
| `RELEASE` | 락 반납 | 실행 → 실행 |
| `ABORT` | 시도 중단(쥔 락을 모두 반납한 것으로 본다) | → 시작(같은 작업의 다음 시도) |
| `FAIL` | 작업 실패(재시도 없음) | → 끝 |
| `END` | 작업 정상 종료(쥔 락 없음) | 실행 → 끝 |

`ABORT`와 `FAIL`은 그 스레드가 쥔 락을 모두 반납하는 사건이다(`RELEASE`를 따로 기록하지 않아도 된다). 재진입 가능 락과 시간 제한 대기는 형식에 없다.

## 2. 락 프로그램으로의 변환 규칙

정책 재생(모드 C)과 오라클(O2)은 작업마다 락 프로그램(획득·반납의 열)을 쓴다. 한 작업의 **마지막으로 정상 종료한 시도**(`END`로 끝난 시도)의 `ACQUIRE`와 `RELEASE` 열이 그 작업의 프로그램이다. 중단된 시도는 프로그램을 정하지 않는다(그 시도의 락 사용은 정책의 영향을 받은 행동이다). 실패한 작업은 변환에서 빠진다. 트레이스가 정책 아래에서 수집된 것이면(합성은 항상 그렇다) 프로그램은 '그 정책에서 관측된 행동'이고 다른 정책 아래에서 같은 프로그램을 쓸 것인가는 O3-18의 쟁점이다.

## 3. 검증기

`python3 -I traces/validate.py <파일.jsonl>`이 다음을 검사하고 요약을 낸다.

1. 머리 레코드의 필드와 형식 이름
2. 필수 필드의 존재와 형, `seq`가 0부터 1씩 증가, `ts`가 줄지 않음, `th`의 범위
3. 스레드별 상태 기계: `BEGIN` 전에 다른 연산이 없음, `REQUEST` 뒤 `ACQUIRE`/`WAIT`/`ABORT`/`FAIL`, `WAIT` 뒤 `ACQUIRE`/`ABORT`, `END`는 실행 상태에서만, 같은 작업의 `attempt`가 `ABORT`마다 1씩 오름
4. 락 배타성: 쥐어진 락의 `ACQUIRE`는 오류, 쥐지 않은 락의 `RELEASE`는 오류, `END` 시점에 쥔 락이 있으면 오류
5. 락 연산 레코드의 `cls`, `mode`가 있음, 한 `lock`은 한 `cls`에만 속함
6. 트레이스 끝에서 아직 끝나지 않은 작업이 있으면 경고(수집이 중간에 끊긴 것일 수 있음)

## 4. 열린 항목

| 번호 | 항목 | 제안 |
|---|---|---|
| O3-2 | L3 사용자 공간 트레이스의 대상 응용 | SI-3 후보: Dimmunix 평가 대상(MySQL, SQLite 등, 문헌 S6) |
| O3-3 | Linux 실행 환경(L4와 모드 R) | 없으면 제외하고 한계로 적는다 |
| O3-18 | 락 인스턴스와 클래스의 구분, P-ORD 순서의 출처, 작업 경계의 정의 | `cls` 필드를 형식에 두었다. 커널 트레이스에서 클래스는 lockdep 클래스, 사용자 공간에서는 락 호출 위치나 초기화 위치를 쓸 수 있다(미검증) |
| O3-20 | 공유(읽기) 모드와 재진입 | v0.1 형식에는 `mode` 필드만 있고 정책이 다루지 않는다 |
| O3-21 | 수집된 트레이스의 라이선스·개인정보 점검 | 수집 전에 점검한다 |
